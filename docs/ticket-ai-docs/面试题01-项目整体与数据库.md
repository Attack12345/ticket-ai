## 一、项目介绍与整体理解（1-10）

### 1. 请用 1 分钟介绍你的项目

【参考答案】
"我做的项目叫 TicketAI，是一个 AI 增强的企业级客服工单系统，解决客服场景的工单全生命周期管理问题：多渠道接入客户请求、自动分派、坐席处理、SLA 超时自动升级。技术栈是 Spring Boot 3.5 + JDK 23 + MyBatis-Plus + MySQL 8 + Redis + Redisson + RocketMQ 5.3 + Elasticsearch 8.14，前端 Vue3。全项目 20 张表、152 个 Java 文件、39 个测试用例。我最有深度的四个设计：一是自研 8 状态 × 12 事件的工单状态机，23 条合法转移，状态变更只有 transition 一个入口，配合乐观锁解决并发；二是 SLA 引擎用 RocketMQ 延迟消息精确到点结算 + 每 5 分钟补偿扫描兜底；三是抢单用 Redisson 分布式锁 + 乐观锁双保险；四是自研 OpenAI 兼容 LLM 客户端，做了自动分类、RAG 回复建议、AI 分派三个增强场景，核心设计原则是 AI 只做增强不做核心流转——LLM 挂了系统照常跑，且每次调用都记录 token 用量做成本可观测。"

### 2. 工单系统的核心业务流程是什么？

【参考答案】
客户消息进线 → 幂等检查（message_no 唯一键防重复提交）→ 创建工单（状态=待分派，启动 SLA 计时并投递延迟消息）→ 异步自动分派 + AI 分类 → 坐席抢单（状态=处理中）→ 回复客户（状态=等待客户）→ 解决 → 关闭。全程受 SLA 监督：超时自动升级（状态=已升级）→ 人工重新分派。已解决的工单会同步进 ES，成为未来 AI 回复建议的参考资料。

【追问】创建工单的事务里做了哪几件事？→ 生成工单号、插入 ticket、写状态日志、建 SLA 计时单、投两条延迟消息、事务提交后发布创建事件。

### 3. 项目里 MySQL、Redis、RocketMQ、ES 各自扮演什么角色？

【参考答案】
MySQL 是事实源：所有业务数据的最终记录，有事务和约束。Redis 是辅助设施：计数器（工单号生成）、分布式锁（抢单）、防重闸门（SETNX 防 AI 重复调用）、登录凭证存储（refreshToken）——数据丢失不影响业务。RocketMQ 是异步通道：SLA 延迟消息（到点检查）和事件通知（工单创建/ES 重试）。ES 是查询索引：知识库分段和已解决工单的全文 + 向量检索，全部数据可从 MySQL 重建。

【追问】Redis 里的数据为什么丢了也不怕？→ 它只存"可重建的辅助状态"：计数器可以从数据库最大值恢复，锁和防重标记过期即失效，refreshToken 丢了用户重新登录即可。事实都在 MySQL。

### 4. 为什么是单体架构而不是微服务？

【参考答案】
两个核心考虑。一是事务一致性：工单状态变更"改状态 + 写日志 + 结算时间戳"必须在一个事务里原子完成，拆成微服务就要引入分布式事务，复杂度远超收益。二是复杂度控制：这个体量（20 表、1-2 万行）单体足够，部署运维简单。但模块边界是按领域划分的（state / mq / es / ai / dispatch 独立包），未来真要拆分，边界是现成的。

【追问】如果拆，服务边界怎么划？→ 工单服务（状态机+主数据）、SLA 服务（天然独立进程：消息消费+扫描）、分派服务、检索服务、AI 服务；事务边界跨服务时用事件驱动最终一致。

### 5. 项目里哪些地方体现了"事件驱动"？

【参考答案】
三处：① 工单创建后发布 TicketCreatedEvent，异步触发自动分派和 AI 分类——创建接口不等待这些慢操作；② 工单解决后发布 TicketResolvedEvent，异步写入 ES 索引；③ SLA 超时发布 SlaTimeoutEvent，SLA 服务和工单服务通过事件解耦（避免循环依赖），状态机消费事件完成升级流转。事件在事务提交后发布，保证异步消费者读到已提交数据。

【追问】事件驱动有什么代价？→ 事件可能丢失或重复投递，所以每个消费者都要幂等：分派失败保持待分派由抢单兜底、AI 分类 SETNX 防重、SLA 升级检查 escalation_triggered。

### 6. 项目里有哪些"幂等"设计？

【参考答案】
六处：① 渠道建单：message_no 唯一键，重复请求返回已建工单；② SLA 延迟消息消费：先查 escalation_triggered 和结算状态，已处理忽略；③ 补偿扫描：查询条件只选"未升级未结算已超时"，重跑无副作用；④ ES 写入：按 id upsert；⑤ AI 分类：SETNX 防重；⑥ 刷新 token：Lua 原子 compare-and-delete。状态机事件 + 乐观锁天然拒绝重复事件。

【追问】为什么"数据库唯一键"比"代码先查再插"可靠？→ 先查再插有并发窗口（两个请求同时查到不存在都去插）；唯一键是数据库约束，第二个插入必然失败，是最终防线。

### 7. 这个项目你最骄傲的设计是什么？

【参考答案】
SLA 引擎的"延迟消息 + 补偿扫描"双保险。它体现了一个分布式系统的核心思想：准时性靠消息（精确到点），最终一致性靠扫描（消息丢了也能兜底），两条检查线查同一张表、走同一套逻辑，且全程幂等。我用 first_response_minutes=1 的策略做过端到端实测验证：1 分钟后未响应工单自动升级，已响应工单不升级。这不是纸面设计，是验证过的。

### 8. 这个项目有什么已知的不足或改进点？

【参考答案】
三个：① timeline 接口没有分页，数据量大时有隐患，应该加游标分页；② AI 分派建议返回的 agentId 没有校验坐席存在性和在线状态，严谨做法是返回前查库确认；③ current_load 冗余字段在工单重派场景没有对旧坐席 -1，口径有边界误差。我清楚每个改进点的方案和优先级，比如 timeline 分页用 id > lastId 游标。

【追问】既然知道有问题，为什么当时不做？→ 当时的范围控制：M4 的 DoD 是"并发正确性"，重派负载修正是 M8 之后的优化项；每个里程碑只承诺当期的验收标准。

### 9. 简历上写"AI 开发模式"，面试官问项目是不是 AI 写的怎么办？

【参考答案】
诚实且有底气地回答："项目全程使用 AI 编码工具开发，但架构设计、技术决策、代码审查都是我的：核心设计（状态机矩阵、SLA 双保险、AI 降级矩阵、幂等总则）是我定的，AI 负责按文档编码；每个里程碑我都做 DoD 验收，踩过的坑（乐观锁缺陷、Redis 版本兼容、RocketMQ 延迟消息配置）是我定位和解决的。AI 提高的是产出速度，不替代理解——你现在追问的任意一行代码我都能讲清楚为什么这么写。设计决策永远是人的决策，工具只是放大效率。"

【追问】那你怎么证明你理解了？→ 接受任意细节追问 + 现场画架构图 + 讲清每个取舍的备选方案。比如"为什么不用 Spring AI"、"为什么延迟消息之外还要扫描"这种问题，没真正做过是答不出权衡细节的。

### 10. 如果让你重新做这个项目，哪些地方你会做得不一样？

【参考答案】
① SLA 结算的"补偿扫描"周期会做成按优先级分级（紧急单 30 秒扫描，普通单 5 分钟）——用成本换准时性；② 工单时间线会做成游标分页；③ 会在分派策略里加"坐席存在性校验"；④ 会考虑把"采纳 AI 分类"做成事件驱动（当前是同步接口）；⑤ 整体架构和核心设计不会变——状态机、双保险、AI 增强的边界，这些是验证过的正确决策。

## 二、技术栈选型（11-20）

### 11. 为什么选 MyBatis-Plus 而不是 JPA？

【参考答案】
JPA 的实体关系映射和自动建表强大，但复杂 SQL 控制弱、隐式行为多（懒加载、级联），性能调优不直观；原生 MyBatis 灵活可控但样板代码多。MP 在 MyBatis 之上提供 BaseMapper 通用 CRUD、分页插件、逻辑删除、自动填充——单表 CRUD 零 XML，复杂查询保留 XML 出口，是开发效率和可控性的平衡点。本项目 20 张表全是单表操作，MP 收益最大化。

### 12. 为什么用 RocketMQ 做延迟消息，不用 Kafka 或 RabbitMQ？

【参考答案】
核心是延迟消息能力：RocketMQ 5.x 的 setDeliverTimeMs 支持任意延迟时长（broker 时间轮实现），语义最贴合 SLA 场景；Kafka 没有原生延迟消息，要自己实现时间轮 + 定时扫描；RabbitMQ 的 TTL + 死信队列方案有队列头阻塞问题（一条长延迟消息会阻塞队列里所有后续消息），且要维护死信转发链路。另外 RocketMQ 的 Spring Boot 集成成熟。

### 13. 为什么用 elasticsearch-java 原生客户端，不用 spring-data-elasticsearch？

【参考答案】
三个原因：dense_vector 和 knn 这些新特性的 API 支持，原生客户端最直接；spring-data 的 repository 抽象对"bool match + 顶层 knn 混合检索"这种复杂查询反而碍事；依赖面小、版本与 ES 服务端严格对应（8.14）。代价是代码略多（手动构建 SearchRequest），但对检索是项目亮点的场景值得。

### 14. 为什么 Redis 用老版本 3.0 而不升级？

【参考答案】
两个原因：一是本机环境已有服务，评估过项目用到的特性——锁（SETNX/Redisson 兼容）、计数器（INCR）、字符串存储、Lua 脚本、过期时间——3.0 全部支持，不需要新版本特性；二是为老版本兼容踩过一个坑：spring-data-redis 3.5 的 expire(key, Duration) 在 Redis 3.0 下触发默认方法递归调用导致 StackOverflowError，所以统一改用 Lua 脚本或 set 带过期参数。结论：**中间件版本匹配要以"实际用到的特性"为准，并实测验证**。

### 15. 为什么用 Redisson 而不是自己写 Redis 分布式锁？

【参考答案】
分布式锁的完整实现有细节：锁的自动过期（防止持有者宕机死锁）、可重入、看门狗续期、公平性。Redisson 是成熟方案，API 一行（tryLock），底层处理了这些边界；自己写 SETNX + EXPIRE 两步会出现"设置完锁还没来得及设过期就宕机"的死锁窗口（必须用 SET key value NX EX 原子命令，容易写错）。**成熟的边界处理交给成熟组件，业务代码专注业务**。

### 16. 为什么用 JWT 不用 Session？

【参考答案】
Session 是服务器内存存会话记录（有状态）：多实例部署要做会话共享，用户多了内存压力大。JWT 是自验证卡片（无状态）：签名 + 过期时间都在卡里，任何实例都能验证，天然支持水平扩展。代价是 token 不能主动作废（只能等过期）——所以本项目把 refreshToken 存 Redis，实现了"可作废 + 单设备"的能力，弥补了 JWT 的短板。

### 17. 为什么用 BCrypt 存密码？

【参考答案】
BCrypt 是专门为密码设计的哈希算法：自带随机盐（相同密码哈希结果不同）、计算代价可调（暴力破解成本高）、不可逆。相比 MD5/SHA 这种"快哈希"（GPU 可以每秒算几十亿次，彩虹表攻击），BCrypt 慢几个数量级，是防暴力破解的标准选择。Spring Security 内置 PasswordEncoder 直接用。

### 18. 为什么前端用 Vue 3 + Element Plus？

【参考答案】
Vue 3 组合式 API 适合中后台管理系统开发，Element Plus 提供完整的表格/表单/弹窗组件，开发效率高；Pinia 做状态管理（token、用户信息、权限码），Vue Router 管理路由，ECharts 做看板图表——都是 Vue 生态的标准组合，维护成本低。

### 19. JDK 23 编译目标为什么设 release=21？

【参考答案】
本机开发用 JDK 23，但把编译目标定为 21：生成的字节码可以在 JDK 21+ 任意环境运行（部署不挑版本），同时用 release 参数而不是 source/target（release 连 JDK 内部 API 也按目标版本约束，更严格）。还踩过 JDK 23 的构建坑：javac 默认 -proc:none 导致 Lombok 不生效，需要在 maven-compiler-plugin 显式配置 proc=full + annotationProcessorPaths——所以 pom 的编译配置全部显式声明，不依赖默认行为。

### 20. 你项目里用到了哪些设计模式？

【参考答案】
① 策略模式：四种分派策略 + 工厂；② 模板方法/状态模式：状态机（矩阵查表，本质是状态模式）；③ 观察者模式：Spring 事件（TicketCreatedEvent 等三个事件）；④ 单例：Spring Bean 默认单例、状态机静态注册表；⑤ 建造者：HttpClient/ES Request 的 Builder API；⑥ AOP：审计注解、全局异常处理。每个模式都能指出具体位置和用途，不是背概念。

## 三、数据库设计（21-35）

### 21. 20 张表怎么分组？为什么这么分？

【参考答案】
6 组：RBAC 权限五表（用户/角色/权限/两个关联）、渠道两表（channel/channel_message 含幂等键）、工单域三表（ticket/ticket_status_log/ticket_comment）、保障三表（sla_policy 策略/ticket_sla 实例/dispatch_strategy 配置）、坐席三表（agent/skill_group/关联表）、内容四表（知识库/分段/审计日志/AI 用量日志）。分组按业务域划分，一组内的表关系紧密，组间只通过外键字段关联。

### 22. 为什么"用户-角色-权限"要拆成五张表？

【参考答案】
因为是多对多关系：一个用户多个角色、一个角色多个用户；一个角色多个权限、一个权限属于多个角色。多对多必须用关联表承载，否则要么字段冗余（用户表塞角色列表），要么权限定义死板（改一个权限要改所有用户）。拆成五表后：加角色、改权限、调整用户角色都是改一行数据，不需要动代码。

### 23. ticket 表为什么有 version 字段？怎么用的？

【参考答案】
version 是乐观锁版本号：所有状态变更的 UPDATE 都带 WHERE version = 读到的值，SET version = version + 1；影响 0 行说明基于过期数据，抛并发冲突。实现上用 UpdateWrapper 显式拼接 version 条件，没有依赖 MyBatis-Plus 的 @Version 注解——因为实测 @Version 拦截器在部分版本组合的更新路径上有参数注入缺陷，而且显式写 SQL 可审计、单测可跑。核心一致性代码不依赖框架魔法。

【追问】如果两个请求都读到 version=5，谁成功？→ 第一个执行 UPDATE 的成功（version 变 6），第二个 WHERE version=5 匹配 0 行失败。

### 24. ticket_status_log 为什么不允许更新和删除？

【参考答案】
它是事件流（Event Sourcing 思想的简化版）：记录"发生过什么"，而不是"当前是什么"。工单历史还原、纠纷仲裁、SLA 结算依据都靠它；更新或删除会破坏审计完整性。所以这张表没有 deleted 字段、没有 UPDATE 需求，设计上就是只增不删。业务表（ticket/agent/kb）用逻辑删除可恢复，流水账物理保留可追溯——两类表的治理策略是分开的。

### 25. 逻辑删除和物理删除怎么选？

【参考答案】
业务数据（工单、坐席、知识库）用逻辑删除：误删可恢复、历史数据可统计，MyBatis-Plus 配置 deleted 字段后对代码透明。流水账（状态日志、审计日志、AI 用量）物理保留，不删除。渠道消息也物理保留（原始报文是证据）。原则：**能影响业务事实和审计的数据不删，普通业务数据软删**。

### 26. 为什么 SLA 策略和实例要分两张表？

【参考答案】
策略是"模板"（规则可以改：中优先级从 2 小时改成 3 小时），实例是"某张工单的固化承诺"（创建时算好的截止时间，不能变）。分两张表：策略怎么改都不影响历史工单的承诺——客户按当时承诺投诉，账算得清。这是"模板与实例分离"的经典设计，和"合同模板 vs 签字的合同"一样。

### 27. ticket 表冗余了 SLA 截止时间，为什么接受冗余？

【参考答案】
列表页和详情页要展示"响应截止、解决截止"，冗余到主表免联表查询；结算依据在 ticket_sla（事实源），主表字段是展示用副本。接受冗余的前提是维护点收敛：两处时间在 SLA 创建时同源写入，改动只在 SLA 创建/结算处发生。**可控冗余换查询性能，是反范式设计的典型取舍。**

### 28. agent 表的 current_load 为什么存表里而不是实时算？

【参考答案】
实时算 = 每次分派都要 COUNT 在途工单，慢；存表 = 抢单时 SQL 原子 +1、关闭时 -1，查询直接读。用可控冗余换速度。代价是维护点必须收敛（只有两处改它），且重派等边缘场景有口径误差——这是已知边界，严谨方案是重派时对旧坐席 -1 或实时 COUNT。

### 29. skill_tags 为什么用 JSON 字符串存？不用关联表？

【参考答案】
技能标签是坐席的轻量属性（["售后","投诉"]），没有独立的业务行为（不像技能组有独立管理页面），用 JSON 列最直接；如果标签将来要独立管理、统计、或者标签本身有属性，再升级成标签表 + 关联表。**结构选型跟着业务复杂度走，不为"规范化"而规范化。**

### 30. 知识库为什么要分段？切分规则是什么？

【参考答案】
分段有两个目的：检索精度（整篇文章几千字，相关度被稀释，切段后精确命中）和 token 成本（RAG 喂给 LLM 的参考资料按量计费）。切分规则：按 Markdown 标题层级切（语义完整）；无标题段落按 500 字定长滑动窗口切、重叠 50 字（防止一句话被窗口边界切断，两边语义残缺）。

【追问】重叠 50 字的代价是什么？→ 内容被索引两次（存储和检索成本略增），换来的是边界语义完整性和召回质量，这个代价值得。

### 31. 为什么向量的"最终存储"在 ES 而不是 MySQL？

【参考答案】
因为相似度计算（knn）是 ES 的强项，MySQL 只能存数字列表、不会算"哪段和这段意思最近"；而且向量可以从文章内容重新生成（embedding 可重建），MySQL 里的文章才是不可丢的事实。**事实存 MySQL，衍生数据存 ES，衍生数据可重建。**

### 32. 索引是怎么设计的？有哪些索引、为什么？

【参考答案】
ticket 表：uk_ticket_no（工单号唯一）、idx_status_priority_create（状态+优先级+创建时间——列表筛选和看板统计的主力查询）、idx_agent_id（查某坐席的工单）、idx_category（分类筛选）。ticket_sla 表：uk_ticket_id（一单一份）+ idx_deadline_status(first_response_deadline, escalation_triggered)——精确匹配补偿扫描的查询条件。channel_message：uk_message_no（幂等键）。**每个索引都能说出对应哪条查询，没有为索引而索引。**

### 33. 为什么索引不是越多越好？

【参考答案】
索引是额外存储 + 每次写入都要更新维护，索引太多写变慢、磁盘占用大；而且优化器可能选错索引。原则：只为高频查询和唯一性约束建索引，用 EXPLAIN 验证走索引。本项目 20 张表的索引都是"查询条件"驱动的。

### 34. demo_data.sql 里有什么？为什么这么造数据？

【参考答案】
约 100 张工单 + 20 篇知识库文章。刻意包含：各状态样本（处理中/已解决/已关闭）、SLA 按时/超时两类样本（超时已升级）、不同优先级和分类分布——保证看板的四个指标（各状态数量、按时率、平均首响、今日新增/解决）有真实可信的数据可看。**演示数据是按业务叙事构造的，不是随机生成的。**

### 35. 如果数据量上亿，工单列表怎么优化？

【参考答案】
分层方案：① 索引覆盖（现有 idx_status_priority_create）；② 按 create_time 月度 RANGE 分区，过期归档；③ 查询强制时间范围（前端默认近 30 天），避免全表扫；④ 读写分离（看板走从库）；⑤ 必要时 ES 承接列表检索（本项目已有 ES 基建）。**先优化查询行为（约束时间范围、分区），再考虑架构变更。**

## 四、工程与测试（36-45）

### 36. 项目的分层架构是什么？各层职责和约束？

【参考答案】
四层：controller（HTTP 处理、参数校验、DTO/VO 转换，薄）、service（业务规则、事务边界、编排）、mapper（MyBatis-Plus BaseMapper）、entity（DO 映射）。依赖方向单向：controller → service → mapper → entity。关键约束：Controller 不写业务逻辑；Service 不返回 DO（返回 VO）、不依赖 HttpServletRequest（用户信息从 UserContextHolder 取）；Mapper 只做数据访问。

【追问】为什么 Service 不返回 DO？→ DO 直接暴露数据库结构：字段名、敏感字段、内部状态都泄出去了；VO 是面向接口的稳定契约，字段裁剪和展示语义都在 VO 层控制。

### 37. 异常体系是怎么设计的？

【参考答案】
业务异常统一 BusinessException(ErrorCode.X)，错误码是枚举（9 个：400/401/403/404/409×3/500/503），禁止散落魔法数字；Controller 不 catch，GlobalExceptionHandler（@RestControllerAdvice）统一处理：业务异常转对应 HTTP 码，兜底异常记 error 日志返回 500。**错误码枚举化 + 全局处理 + 兜底日志，三件事保证错误处理不会乱。**

### 38. 事务是怎么用的？跨 MQ 的操作怎么保证一致性？

【参考答案】
写操作 Service 方法加 @Transactional(rollbackFor = Exception.class)——rollbackFor 指定"任何异常都回滚"（默认只回滚 RuntimeException，checked 异常不回滚，容易踩坑）。跨 MQ 的模式是"先落库后发消息"：SLA 计时单先插入（本地事务），再投延迟消息，发送失败不抛异常由补偿扫描兜底——数据是事实源，消息只是提醒，所以不存在"事务和消息不一致"问题。

### 39. 39 个测试用例覆盖了哪些关键点？

【参考答案】
状态机全矩阵（23 条合法转移 + 10+ 条非法断言）、乐观锁冲突、10 线程并发抢单（恰好 1 成功）、SLA 结算分支（按时/超时/已升级忽略）、补偿扫描、渠道幂等（重复 messageNo 返回同一工单）、分派工厂（权重降序、全失败返回 null）、AI 降级（LLM 不可用各场景表现）、SETNX 防重、分段切分。**测试集中在规则密度最高的地方：状态机、并发、幂等、降级。**

### 40. 测试为什么不允许连真实中间件？

【参考答案】
① 可重复性：CI 环境没有 MySQL/Redis/MQ/ES，连真实中间件的测试在别人机器上跑不起来；② 确定性：真实中间件有随机性（网络、时序），断言不稳定；③ 速度：单元测试要毫秒级跑完。所以用 Mockito mock 依赖、H2 模拟数据库——**单元测试验证的是逻辑正确性，中间件兼容性用端到端冒烟单独验证**。

### 41. 日志系统怎么设计的？traceId 是什么？

【参考答案】
logback + TraceIdFilter（OncePerRequestFilter）：每个请求生成一个 traceId 放入 MDC，业务日志自动带上——一个请求跨多个方法/异步任务的日志能串起来排查。级别约定：业务操作 info、异常 warn/error。**分布式排查的第一抓手就是链路 ID。**

【追问】异步任务里的 traceId 会丢吗？→ 会——MDC 是线程局部变量，异步线程拿不到主线程的 traceId。严谨做法是在异步任务提交时手动把 traceId 传进去（本项目异步链路未传，是已知改进点）。

### 42. 项目怎么保证代码质量？（单人项目怎么证明）

【参考答案】
可验证的证据链：① 39 个自动化用例可重复跑；② 每个里程碑 DoD 验收清单（M3 的 1 分钟 SLA 实测）；③ 开发文档锁定了架构分层、异常体系、命名规范并被执行；④ git 按 Conventional Commits + 里程碑 tag，演进可追溯。**单人项目更需要把"验证"制度化，否则就是自嗨。**

### 43. 接口返回结构统一吗？怎么统一？

【参考答案】
统一 Result<T>：{code, message, data, timestamp}——code 用 HTTP 语义（200 成功、409 冲突…），message 给前端提示语，data 是业务数据；分页套 PageResult（records/total/page/size/pages）。前端 axios 拦截器统一解包：code 非 200 弹提示。**统一返回结构让前端处理逻辑收敛在拦截器一处。**

### 44. 你怎么做 API 文档？怎么调试接口？

【参考答案】
knife4j（OpenAPI3 的增强版，Spring Boot 3 兼容）——注解驱动自动生成接口文档，带调试界面，接口契约以注解为准不会和代码脱节。联调期也用它做手工验证（比如验证非法流转返回 ILLEGAL_TRANSITION）。**文档生成和代码同源，不会出现"文档更新了代码没更新"。**

### 45. 项目上线（部署）方案是什么？

【参考答案】
当前是本地开发环境：MySQL/Redis 是 Windows 服务，ES/RocketMQ 是 Docker Compose 编排（restart: unless-stopped），后端 mvn spring-boot:run 起在 8090，前端 Vite dev 起在 5173。生产化演进方向：后端打 jar 包 + systemd/容器化，前端 npm run build 出静态资源由 Nginx 托管，中间件全容器化并做数据卷持久化——这个演进路径在 README 里写清楚了。
