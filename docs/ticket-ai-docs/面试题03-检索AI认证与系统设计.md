## 一、检索与 ES（1-9）

### 1. 全文检索和向量检索的区别？为什么项目里两个都用？

【参考答案】
全文检索（ES match）基于分词 + 倒排索引，匹配**字面**：搜"退货"就是字面上的退货；向量检索基于 embedding 把文字变成坐标，匹配**语义**："手机屏幕碎了"能找到"液晶面板破损"。两者互补：全文检索精确可解释，向量检索能跨字面找同义内容。项目里知识库检索用 bool match + 顶层 knn 混合，ES 自动合并分数排序。

### 2. 倒排索引是什么？为什么比 LIKE 快？

【参考答案】
倒排索引存"词 → 出现在哪些文档"：搜"退货"直接取词表里的文档列表，复杂度 O(1) 级别；MySQL LIKE 是逐行扫描全文匹配，O(N)。**以空间换时间：写入时多存一份词表，查询时直接查表。**

### 3. 为什么知识库要分段进索引？

【参考答案】
两个原因：① 检索精度——整篇几千字，只有一段讲退货，整篇匹配分被稀释；切段后精确命中相关段。② token 成本——RAG 喂给 LLM 的参考资料按量计费，取 500 字段落比取整篇文章省钱。切法：按 Markdown 标题层级切，无标题按 500 字定长滑动窗口、重叠 50 字防语义断裂。

### 4. MySQL 和 ES 的数据一致性怎么保证？（三级保障）

【参考答案】
① 同步写：kb_segment 落库后立即 upsert ES；② 失败重试：同步失败发 es-sync-retry 普通消息，重试 3 次；③ 对账补偿：EsSyncCompensationTask 每 10 分钟对比 MySQL 与 ES 的 id 差集补写。方向永远是"从 MySQL 补 ES"——**MySQL 是事实源，ES 是可重建索引**，ES 炸了删索引重建，业务零损失。

### 5. 为什么 ES 是可重建的？什么是"事实源"？

【参考答案】
事实源 = 数据的最终权威记录：有事务、有约束、能恢复。ES 的全部数据（分段内容、工单标题描述）都来自 MySQL，向量还可以重新 embedding 生成——所以 ES 是"衍生数据"，衍生数据丢了可以从事实源重建。**架构决策：先写事实源，再同步索引；索引可重建，事实不能丢。**

### 6. 为什么用 elasticsearch-java 原生客户端？

【参考答案】
① dense_vector / knn 新特性 API 支持最直接；② spring-data-elasticsearch 的 repository 抽象对"bool match + knn 混合"复杂检索反而碍事；③ 依赖面小、版本与服务端严格对应。**少一层抽象 = 少一层不确定性，检索是项目亮点，值得直接控制。**

### 7. knn 在 API 里是"顶层参数"——这个细节有什么坑？

【参考答案】
elasticsearch-java 里 knn 是 SearchRequest.Builder 的顶层方法（builder.knn(...)），不是 bool query 的子查询——写错过的人容易把 knn 塞进 query 里导致编译错误或行为不对。这个细节来自真实开发（elasticsearch-java 8.14 的 API 设计），说明**框架 API 细节要靠实践踩过才知道**。

### 8. ES 挂了系统会怎样？

【参考答案】
分场景降级：写入失败进重试队列 + 对账补齐（恢复后自动补）；检索失败 catch 返回空列表；回复建议链路 ES 返回空 → prompt 无参考资料 → LLM 基于常识回复并建议人工跟进；similarTickets 空向量返回空。启动时 EsIndexInitializer 建索引失败也只是记日志不阻断启动。**ES 是增强层不是核心依赖——和 AI 降级同一哲学。**

### 9. 已解决工单为什么要进索引？处理中的为什么不进？

【参考答案】
ticket_index 的用途是"相似工单召回"——给 AI 回复建议当参考资料。只有已解决的工单才有"解法"价值（处理方案可复用）；处理中的工单没有结论，进了反而污染召回质量。**索引内容要服务于用途，不是全量搬运。**

## 二、AI 模块与 RAG（10-19）

### 10. 为什么自己写 LLM 客户端，不用 Spring AI？

【参考答案】
三点：① 能力需求窄——只需要 chat 和 embeddings，一个 HTTP 封装 170 行覆盖，引入框架是为 10% 需求付 100% 学习成本；② 错误分类与降级要完全自控——把失败精确分类为"没配密钥/超时/限流/服务端错误/返回格式非法"，每种走不同降级路径（静默、报 503、返回 null），框架异常体系没有这个粒度；③ 协议透明可替换——直接对接 OpenAI 兼容协议，base-url 配置化，换厂商只改配置。另外把"每次调用写 ai_usage_log"内建进客户端，成本可观测是项目级要求。**每个"不用框架"的理由背后都有具体项目诉求。**

### 11. 怎么保证 LLM 返回合法 JSON？

【参考答案】
三层：协议层 response_format={"type":"json_object"}（服务端约束）；提示词层明确输出格式和取值集合（{"category": "售后|售前|投诉|咨询|其他", ...}）；代码层返回后 objectMapper.readTree 校验，非法抛 PARSE_ERROR 走降级。**提示词约束是软约束，代码校验是硬兜底。**

### 12. 三个 AI 场景分别是什么？各怎么降级？

【参考答案】
① 自动分类：异步执行，SETNX 防重，结果写 ai_* 建议字段；LLM 失败静默降级（坐席手工分类）。② RAG 回复建议：坐席主动点击触发，ES 召回相似工单和知识库 → LLM 生成草稿 + 引用；LLM 失败返回 503 明确提示（主动操作必须可感知失败）。③ AI 分派建议：仅策略启用时调用，返回 agentId 或 null；失败返回 null 交给下一个策略。

### 13. 为什么分类失败静默、回复建议失败报 503？

【参考答案】
触发方式决定反馈方式：分类是后台自动任务，失败了没人等它，静默降级即可（ai_category 空、坐席手工分类）；回复建议是坐席主动点击等结果的操作，必须明确反馈"AI 暂不可用"，否则坐席以为在生成、白等。**降级策略跟随用户预期：被动任务无感降级，主动操作明确报错。**

### 14. RAG 的完整流程是什么？

【参考答案】
① 工单内容 embedding 转查询向量；② 召回：已解决工单 knn top3 + 知识库 match+knn top3；③ 组装 prompt：系统提示（资深客服、参考资料、输出 JSON、不超 500 字、不得编造政策）+ 客户问题 + 参考资料；④ chatJson 生成回复草稿和引用列表；⑤ 前端展示可编辑草稿 + 可展开核实的引用；⑥ 坐席编辑后点发送才真正回复。**检索真实引用 + 人审后发送 + 禁止编造，是 RAG 落地的三件套。**

### 15. 引用的 kbRefs 是 LLM 生成的还是召回时收集的？

【参考答案】
召回时真实收集的：检索阶段就把命中的"相似工单号"和"知识库标题"收集进引用列表；LLM 的 kbRefs 只是参考。这是刻意设计——如果让 LLM 自己生成引用，它会幻觉出不存在的文档（很多 RAG 方案的经典翻车点）。**引用与内容同源：看到什么引用，内容就在 prompt 里。**

### 16. SETNX 防重具体怎么做的？为什么需要？

【参考答案】
SETNX ai:classify:{工单Id}（不存在才写入成功，TTL 600s）：写成功才执行分类，执行完 finally 删除。原因：LLM 调用按 token 计费，事件重复投递（MQ 重试、应用重启重放）会导致同一工单被重复调用、重复花钱。**异步任务必须自己保证幂等——和 SLA 消息消费同一个思想。**

### 17. ai_usage_log 记录了什么？有什么用？

【参考答案】
场景、模型、输入/输出/总 token、耗时、成败、错误信息。用途：成本核算（token 就是钱）、质量监控（失败率/延迟趋势）、异常定位（错误留痕）、场景分析。**AI 调用可观测 = AI 工程化**——区别于"调了 API 完事"的分水岭。

### 18. 为什么 reply 要限制 500 字？怎么限制？

【参考答案】
客服回复要简洁专业，过长体验差且容易让 LLM 编造细节。限制双层：提示词约束"不超过 500 字"（软约束）+ 代码 reply.substring(0, 500) 截断（硬兜底）。**LLM 工程原则：提示词约束永远要有代码兜底。**

### 19. 如果完全没配置 LLM key，系统能跑吗？

【参考答案】
能，全流程可跑：LlmClient 第一行检查 apiKey 为空抛 NO_KEY（快速失败不等待超时）→ 分类静默降级、回复建议 503、AI 分派返回 null、embedding 失败跳过向量字段走纯全文。**零依赖运行是"AI 只做增强"的验收标准：LLM 挂了系统慢一点笨一点，但照常转。**

## 三、认证安全（20-33）

### 20. 认证和授权的区别？项目里分别在哪实现？

【参考答案】
认证 = 你是谁（登录核对密码，签发 JWT）；授权 = 你能干什么（@PreAuthorize 接口层 + 状态机 transition 内 checkPermission 核心层）。先认证后授权：过滤器验完 token 才放行进接口，接口和核心链路再做权限校验。

### 21. JWT 的结构是什么？为什么能防篡改？

【参考答案】
三部分：Header（算法）、Payload（数据：userId/username/agentId/permissions/过期时间）、Signature（用密钥对前两部分算的签名）。防篡改原理：任何修改都会导致签名不匹配，服务器验签直接失败。注意 payload 是 base64 编码不是加密，**敏感信息（密码）绝不能放 JWT**。

### 22. 为什么用双 token？各自的职责？

【参考答案】
单 token 的取舍矛盾：有效期短被盗损失小但体验差，有效期长体验好但被盗损失大。双 token 分工：access（30 分钟）每次请求带，被盗窗口小；refresh（7 天）只用于换新卡，不随请求传输，暴露面小，且存 Redis 可作废。**短时效凭证 + 长时效续期凭证，是安全与体验的平衡。**

### 23. refreshToken 为什么要存 Redis？

【参考答案】
两个原因：① 可作废——JWT 本身无法主动作废（只能等过期），把 refresh 存 Redis，改密码/安全事件时删 key，所有会话立即失效；② 单设备语义——新登录覆盖旧 token，旧设备刷新时比对失败必须重新登录（滚动替换）。

### 24. 刷新为什么必须用 Lua 原子脚本？

【参考答案】
刷新三步（读 Redis 值 → 比对 → 删除）Java 分步做有并发竞态：黑客偷了旧 token 同时发两个刷新请求，两个都读到旧值、都比对通过、都成功——旧 token 被用两次，安全防线击穿。Lua 脚本在 Redis 单线程模型下原子执行：第一个执行完 key 已删，第二个返回 0 被拒绝。**读-比-删必须原子，Redis Lua 是标准解法。**

### 25. 权限码为什么要放进 accessToken？

【参考答案】
无状态校验：过滤器解析 token 直接构建 LoginUser（含权限码列表），每次请求不查数据库——性能好、多实例无共享状态。代价：改权限要等 token 过期（30 分钟）生效。**无状态认证的典型取舍：用 token 内嵌权限换请求性能，接受权限变更延迟。**

### 26. 授权为什么有两层？@PreAuthorize 和状态机校验的区别？

【参考答案】
@PreAuthorize 是接口层闸门——防无权限用户调接口；状态机 checkPermission 是核心链路闸门——即使有人绕过 Controller 直接调 service（内部 bug、接口缺失），矩阵的权限要求依然生效。**权限要求写在状态机矩阵里，是业务规则的一部分，不是接口装饰。**

### 27. JwtAuthenticationFilter 做了什么？UserContextHolder 是什么？

【参考答案】
过滤器：取 Authorization: Bearer 头 → 无 token 放行（接口自己决定）→ 验签名 + 过期（无效 401）→ 构建 LoginUser 放入 UserContextHolder（ThreadLocal，当前请求线程的"用户口袋"）→ 请求结束清除。Service 层从口袋拿 userId/username/agentId，不碰 HttpServletRequest——**分层解耦：Service 不依赖 HTTP 细节，测试好 mock。**

### 28. 为什么渠道建单接口是公开的？怎么防滥用？

【参考答案】
客户通过网页表单/邮件进线，没有系统账号，接口必须公开。防护：① message_no 幂等键（重复请求返回同一工单，防止重复建单）；② 参数校验（标题/内容长度）；③ 已知改进点：IP 限流、渠道级 quota。**面向外部用户的入口与内部管理入口分离，防护强度不同。**

### 29. 密码怎么存的？为什么不用 MD5？

【参考答案】
BCrypt 哈希（Spring Security PasswordEncoder）：自带随机盐（相同密码结果不同）、计算代价可调、慢（暴力破解成本高）。MD5/SHA 是快哈希，GPU 每秒几十亿次，配合彩虹表秒破。**密码存储用专用慢哈希，是安全底线。**

### 30. 审计日志记什么？怎么实现的？

【参考答案】
敏感操作（分派/关闭/升级/取消/SLA 策略变更）记：action、target_type/target_id、detail_json、ip、操作人、时间。实现：@Audited(action="TICKET_ASSIGN") 注解 + AOP 切面自动写 audit_log；SLA 系统升级也审计（username=system）。**系统行为和人一样要留痕，审计是全员的。**

### 31. 401 后前端怎么处理？怎么自动续期？

【参考答案】
axios 响应拦截器：收到 401 → 用 refreshToken 调 /auth/refresh → 成功更新 token 并**重放原请求一次**（用户无感）；refresh 也失败 → 清登录态跳 /login。注意排除 refresh 接口自身避免死循环。**双 token 的体验价值在前端这一行重放逻辑上兑现。**

### 32. JWT 的密钥怎么管理？生产环境有什么升级空间？

【参考答案】
本项目 HS256（对称密钥），密钥配置化、环境变量注入不入 git。生产升级方向：RS256 非对称（私钥签名、公钥校验）——多服务共享验证时不用分发密钥，且私钥泄露可以轮换。**知道当前方案的边界和升级路径，是安全认知的体现。**

### 33. 权限变更（比如给角色加权限）什么时候生效？

【参考答案】
权限码打包在 accessToken 里，最迟 30 分钟（token 过期）生效；另有 5 分钟权限缓存刷新方案（文档标注）可加速。**这是"无状态认证"的固有取舍：状态在卡里，卡没换，状态不变。**

## 四、系统设计与扩展（34-45）

### 34. 如果要求 SLA 结算"秒级准时"，怎么改？

【参考答案】
当前误差来源是补偿扫描周期（5 分钟）——延迟消息本身是毫秒级投递。方案：① 缩短扫描周期（30s，代价是 DB 查询频率上升）；② 分级扫描：紧急工单高频扫描、普通单低频（用成本换准时性）；③ 消息消费失败场景加死信重投。**先分析误差来源，再按成本-时效权衡选方案。**

### 35. 单表数据过亿，工单列表怎么优化？

【参考答案】
① 索引覆盖（现有 idx_status_priority_create）；② 按 create_time 月度 RANGE 分区 + 过期归档（关闭超一年迁冷库）；③ 查询强制时间范围（前端默认近 30 天）；④ 读写分离（看板走从库）；⑤ 必要时 ES 承接列表检索（项目已有 ES 基建）。**先优化查询行为和存储布局，再考虑架构变更。**

### 36. 如果拆微服务，事务边界怎么处理？

【参考答案】
拆分后最大问题是 transition 的原子性（状态+日志+时间戳）跨服务：方案是工单服务保持本地事务，其他服务（SLA、分派、检索、AI）通过事件驱动最终一致——每个消费者都有幂等设计（escalation_triggered、SETNX、消息唯一键）。**拆分不是消灭一致性，是把强一致收敛到本地、跨服务用最终一致。**

### 37. 怎么评估"AI 自动回复客户"（不经过人工）这个需求？

【参考答案】
分析框架：① 风险——LLM 幻觉回复的法律/口碑风险，必须有兜底；② 分级方案——只对"高置信度 + 低风险类别"（如咨询类，confidence > 0.9）自动回复，规则库或 LLM+规则双校验，其余转人工；③ 可观测——现有 ai_usage_log 基础上加"自动回复采纳率/投诉率"指标；④ 熔断——投诉率超标自动关闭自动回复。**不是不能做，而是要有控制地做：分级、兜底、可观测、可熔断。**

### 38. 怎么做压测？关注什么？

【参考答案】
压核心接口（建单、列表、抢单、ai-suggest），关注 TPS、P95/P99 延迟、错误率；并发抢单用专门脚本验证正确性（成功数=1）。指标红线：建单 P95 < 500ms、列表 < 300ms、高并发无脏数据。中间件水位：Redis 命中率、ES 查询耗时、MQ 堆积。**正确性压测（并发语义）比吞吐数字更能体现工程能力。**

### 39. 项目里"可观测性"体现在哪些地方？

【参考答案】
① ai_usage_log：LLM 成本/质量全量留痕；② audit_log：敏感操作全量审计；③ TraceIdFilter：请求全链路串联日志；④ ticket 冗余字段：assign_strategy（分派策略命中记录）、SLA 时间戳——业务状态一眼可见。**可观测性 = 出了问题能定位 + 长期能分析。**

### 40. 消息队列的消费失败重试策略是什么？

【参考答案】
SLA 延迟消息：RocketMQ 默认 16 次退避重试；重试耗尽仍失败 → 消费者 catch 记日志不抛 → 补偿扫描兜底。**消息系统不承诺"一定成功"，承诺"失败痕迹可发现、有兜底路径"。**

### 41. 怎么防止"消息风暴"或者 MQ 堆积？

【参考答案】
本项目场景 MQ 量很小（每工单 2 条延迟 + 少量事件），堆积风险低。通用方案：消费端限流（线程池控制消费速率）、报警监控堆积量、生产者合并消息。**先评估量级再决定要不要治理——当前量级不需要过度设计。**

### 42. 为什么"AI 建议"字段和"正式字段"分离？

【参考答案】
AI 会错，建议字段错了不影响业务（坐席采纳才生效）；正式字段是业务事实（分派、统计依赖它）。分离带来的额外收益：ai_category vs category 的差异天然构成"AI 效果标注集"——坐席采纳 = 正样本，修改 = 反样本，未来可以做模型迭代。**一个设计两个收益：安全边界 + 数据资产。**

### 43. 系统支持多租户吗？怎么扩展？

【参考答案】
当前单租户。扩展方案：① 最轻量——加 tenant_id 字段 + MyBatis-Plus TenantLineInnerInterceptor 自动拼接租户条件，索引改复合索引；② 重方案——独立实例（隔离强、成本高）。**租户隔离级别（字段级 vs 实例级）是商业与成本的权衡，先说清楚场景再选。**

### 44. 怎么保证"改代码不影响状态机矩阵"这种核心规则？

【参考答案】
三层：① 代码结构——矩阵收敛在 StateMachineRegistry 静态块，改动位置唯一；② 测试锁定——StateMachineTest 全量断言 23 条合法 + 非法，改了矩阵测试就红；③ 评审流程——开发文档明确"矩阵变更需要评审"，核心规则变更必须过验收。**规则的正确性靠测试锁定，不是靠自觉。**

### 45. 如果客户要求"工单必须支持附件"，怎么设计？

【参考答案】
① 存储选型：小文件存 MySQL（BLOB 或 base64），大文件存对象存储（MinIO/OSS）——生产用对象存储；② 表设计：ticket_attachment 表（ticket_id、文件名、大小、存储路径、上传人），一对多关联；③ 权限：附件继承工单的访问权限（客户渠道接口只能看 visibility=ALL 的附件）；④ 安全：上传类型白名单 + 大小限制 + 文件名消毒（防路径穿越）。**功能扩展的完整思考框架：存储 + 表结构 + 权限 + 安全。**

## 五、行为与情景（46-55）

### 46. 你在这个项目里遇到最难的 bug 是什么？

【参考答案】
（选 MyBatis-Plus 乐观锁坑）现象：用 @Version 注解做乐观锁，version=0 的实体更新报 MP_OPTLOCK_VERSION_ORIGINAL not found。排查：查源码发现是拦截器对实体更新路径的参数注入缺陷，且 LambdaUpdateWrapper 的 lambda 解析依赖 MP 运行时缓存、纯单测环境不可用。解决：核心路径（transition/claim）改用 UpdateWrapper 显式拼接 version 条件——语义一致、SQL 可审计、单测可跑。**回答结构：现象 → 排查 → 根因 → 解法 → 沉淀（教训：核心一致性逻辑不依赖框架魔法）。**

### 47. 如果面试官说"这个项目很小，没什么难度"，你怎么回应？

【参考答案】
"体量小是刻意的选择——1-2 万行、20 张表，任何一行代码都能被追问，这是我完全掌控的边界。但体量小不代表深度浅：状态机矩阵、SLA 双保险、抢单双锁、RAG 降级矩阵，每个都是分布式系统里的真实难题，而且都有测试和实测验证。我认为对面试而言，把 20 张表、152 个文件讲透，比贴一个看不懂的大项目有价值得多。"

### 48. 你的技术短板是什么？

【参考答案】
"短板是生产环境经验——项目跑在本机，没经历过真实的高并发线上流量。我对这个短板有补偿：并发正确性用测试验证（10 线程抢单）、容量边界在设计里预留（分区/归档/读写分离的演进路径），并且正在学习 ES 集群和 RocketMQ 高可用的部署运维。"

### 49. 你 8 周开发计划怎么安排的？为什么这么排？

【参考答案】
M1 骨架+状态机（最难的正确性先做）→ M2 渠道+坐席（幂等）→ M3 SLA（延迟消息+扫描+实测）→ M4 分派+并发（10 线程测试）→ M5 知识库+ES（双写补偿）→ M6 AI（降级矩阵）→ M7 看板+审计+前端 → M8 演示数据+冒烟。原则：**风险前置**（状态机/并发是正确性最难的部分，放前中期验证）、**每期可验收**（DoD 清单，比如 M3 必须 1 分钟策略实测通过）、**依赖排序**（上层依赖下层，SLA 依赖状态机，AI 依赖 ES）。

### 50. 怎么证明项目是你写的而不是抄的？

【参考答案】
三条证据：① 架构决策有取舍痕迹——每个选型都有"为什么不用别的"（自研客户端 vs Spring AI、延迟消息 vs 定时任务、显式乐观锁 vs @Version），抄来的项目讲不出备选方案的对比；② 踩坑细节——@Version 缺陷、Redis 3.0 兼容、RocketMQ 延迟消息配置，这些是动手才踩得到的；③ 测试和实测——1 分钟 SLA 实测、10 线程并发断言，是验证驱动开发留下的证据。**随时欢迎追问任意细节。**

### 51. 你希望面试官怎么评价你的这个项目？

【参考答案】
三点：一是架构克制——每个"不引框架/不拆服务"的决策都有理由；二是一致性思维——幂等、补偿、对账、双保险不是名词而是落地代码；三是可验证——每个关键设计都有测试和 DoD 证据。**如果追问完发现"说的每句话都能在代码里找到对应"，就是我最想达到的效果。**

### 52. 让你带一个新人讲这个项目，你从哪讲起？

【参考答案】
先讲业务（什么是工单、系统解决什么问题）→ 再画整体架构图（组件角色）→ 然后按"一次请求的旅程"串起来（建单→分派→抢单→回复→解决）→ 最后深入核心机制（状态机、SLA、并发、AI）逐个讲。**顺序：业务 → 架构 → 链路 → 机制，由外到内，和我的学习文档顺序一致。**

### 53. 项目里 AI 部分的"成本控制"除了 token 记录还有什么？

【参考答案】
① 模型选型：轻量模型（gpt-4o-mini 级别）做分类/建议，不用大模型；② 防重复调用：SETNX 防重 + 异步单次执行；③ 检索只取 top3 + 分段 500 字：喂给 LLM 的上下文体积可控；④ 超时 15s：快速失败不烧钱空等。**成本控制是设计出来的：选型、防重、上下文裁剪、快速失败。**

### 54. 如果老板说"AI 分类老出错，把它下线"，你怎么处理？

【参考答案】
① 先量化：查 ai_usage_log + 建议/采纳差异，算出真实准确率——"老出错"是感觉还是数据？② 定位：是模型问题、prompt 问题、还是工单本身信息不足？③ 分层方案：全量下线 vs 只对高置信度启用（confidence > 0.9 的建议保留，其余不展示）；④ 数据说话：给老板看准确率趋势和采纳率，让决策有依据。**先量化再决策，用数据管理系统里的情绪化决策。**

### 55. 你接下来想学什么？和这个项目有什么关系？

【参考答案】
三个方向：① 深入 RocketMQ——事务消息、消息轨迹、高可用部署（项目用了延迟消息但没用事务消息，想把这块补上）；② ES 集群运维——分片、副本、滚动升级（项目用了检索但没跑过集群）；③ 向量检索进阶——混合检索的 RRF 融合、BM25 与向量分数调优（项目是 ES 自动合并，想自己控制权重）。**方向都和项目强相关：不是漫无目的学，是项目边界外的延伸。**
