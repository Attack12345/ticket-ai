## 一、状态机（1-18）

### 1. 什么是状态机？为什么工单系统需要它？

【参考答案】
状态机 = 状态 + 事件 + 转移规则表：某个状态下发生某个事件，只能按规则表变成指定的目标状态，非法组合一律拒绝。工单系统需要它是因为：① 管规矩——"已关闭"不能随便回到"处理中"，所有流转必须合法；② 留流水——每次流转自动写 ticket_status_log，历史可还原、纠纷可仲裁；③ 控权限——每条转移自带权限要求，权限不够直接拒绝。没有状态机就是 if-else 满天飞，状态乱改、无据可查。

### 2. 项目里状态机有几种状态、几种事件、多少条转移？

【参考答案】
8 个状态：NEW、PENDING_ASSIGN、PROCESSING、WAITING_CUSTOMER、RESOLVED、CLOSED、ESCALATED、CANCELLED。12 个事件：SUBMIT、AUTO_ASSIGN、MANUAL_ASSIGN、CLAIM、REPLY、CUSTOMER_REPLY、RESOLVE、CLOSE、REOPEN、ESCALATE、TIMEOUT_ESCALATE、CANCEL。23 条合法转移，CANCELLED 是终态无出口。

### 3. 为什么状态机自研，不用 Spring StateMachine 或 Flowable？

【参考答案】
三点：① 需求匹配——8 状态 × 12 事件的规则表，一个枚举 + EnumMap 静态注册表就装下了，第三方流程引擎带来的部署模型、持久化、类加载复杂度远超需求；② 可控可测——矩阵是代码事实，编译期验证、git 可追溯、测试可全量断言（23 条合法 + 非法断言），第三方引擎的行为是黑盒；③ 和项目其他设计咬合——allowedEvents 直接暴露给前端驱动按钮，transition 的乐观锁并发控制，这些和自研矩阵天然一体。**选型原则：能力边界内的东西自己实现，把复杂度留给真正需要的地方。**

### 4. transition() 的完整流程是什么？

【参考答案】
五步：① 查工单（不存在抛 404）；② 状态机校验——StateMachine.getTransition(当前状态, 事件)，查不到抛 ILLEGAL_TRANSITION（消息带状态和事件名）；③ 权限校验——非 SYSTEM 事件检查当前用户权限码，缺失抛 403；④ 乐观锁更新——UPDATE 带 WHERE id + version + 当前状态，SET 目标状态 + version+1 + 事件后置动作（时间戳/归属），影响 0 行抛 409 并发冲突；⑤ 写状态日志（from/to/event/operator），RESOLVE 时发布已解决事件触发异步索引写入。

### 5. 为什么事件后置动作（时间戳、归属）要和状态变更放同一条 UPDATE？

【参考答案】
原子性：两条 SQL 之间有并发窗口，别的请求可能读到"状态已变但时间戳没写"的中间态——SLA 结算读到 first_responded_at 为空就会误判超时；一条 UPDATE 的状态 + 时间戳 + 归属由数据库保证同时生效。性能上还少一次 SQL。**能一条语句原子完成的事，绝不用两条。**

### 6. 为什么状态变更必须收敛到 transition() 一个入口？

【参考答案】
单入口保证四个不变量：状态机合法性（只有矩阵内流转能发生）、权限校验（每步操作都有权限要求）、全量流水（每次流转都有状态日志）、并发安全（统一的乐观锁模式）。任何一处绕过（直接 UPDATE status）都会破坏审计完整性——状态日志是事件流，缺了事件，工单历史就无法还原，SLA 结算依据也会失真。

### 7. 乐观锁和状态机是怎么配合的？

【参考答案】
分工：状态机管"合法性"（这个状态能不能做这个操作），乐观锁管"一致性"（并发下这个操作只能成功一次）。transition() 里先做矩阵校验（读到的状态 + 事件是否合法），再带 version 条件 UPDATE（写的时候如果版本被改过就拒绝）——两个请求基于同一状态并发操作，后提交的影响 0 行抛冲突。**业务规则与并发控制在同一条链路上完成。**

### 8. SYSTEM 事件有哪些？怎么保证只有系统能触发？

【参考答案】
AUTO_ASSIGN、CUSTOMER_REPLY、TIMEOUT_ESCALATE 三个。Transition.requiredPermission 标记为 SYSTEM，transition() 跳过用户权限校验——但安全不靠"跳过校验"：这三个事件没有对外 HTTP 入口，只能由系统内部链路触发（自动分派监听器、客户渠道消息消费、SLA 升级事件监听器），用户永远无法直接调用。**权限校验 + 入口隔离双保险。**

### 9. 非法流转会怎样？前端看到什么？

【参考答案】
抛 BusinessException(ILLEGAL_TRANSITION)，message 形如"当前状态[已关闭]不允许事件[REPLY]"，HTTP 409，全局异常处理器统一转 Result 返回，前端弹提示"非法的工单状态流转"。StateMachineTest 对 10+ 条非法组合有断言——**非法流转是被测试锁定的行为，不是碰运气。**

### 10. WAITING_CUSTOMER 的自环转移（REPLY → WAITING_CUSTOMER）为什么存在？

【参考答案】
业务语义：坐席在等待客户时还可以继续回复（比如补充说明、催客户），操作合法但状态不用变。自环 = "同状态下的重复合法操作"，状态机要贴合业务语义而不是追求"无自环"的数学完美。如果拒绝自环，坐席等客户期间连补充说明都发不出去。

### 11. 新增一个状态（比如 PAUSED 暂停）需要改哪些地方？

【参考答案】
① TicketStatus 枚举加 PAUSED(9)；② StateMachineRegistry 注册 PAUSED 相关的转移（PROCESSING --PAUSE--> PAUSED、PAUSED --RESUME--> PROCESSING）及权限；③ 前端按钮自动联动（allowedEvents 是状态机暴露的）；④ StateMachineTest 补断言；⑤ 业务侧要考虑：PAUSED 期间 SLA 计时要不要暂停？如果暂停，SLA 引擎要支持"计时冻结"逻辑——**加状态容易，状态对既有机制的影响要想清楚**。核心收益：矩阵驱动一切，改动收敛在注册表。

### 12. 为什么矩阵用静态注册表而不是数据库配置？

【参考答案】
规则是"代码事实"：编译时写错就编译失败，git 能追溯谁改的，测试能全量断言。数据库配置的规则没有版本控制、改错了出生产事故都不知道哪次改的。**核心业务规则用代码固化，是工程上的刻意选择。**

### 13. 工单创建时状态是什么？NEW 状态为什么存在但没用？

【参考答案】
当前创建即插入 status=2（PENDING_ASSIGN），同时写一条 NEW → PENDING_ASSIGN / SUBMIT 的状态日志——"创建即提交"。NEW 和 SUBMIT 在枚举和矩阵里保留，是为了给草稿功能留演进空间：未来支持"先存草稿不提交"，只需改 create 的插入状态并开放 SUBMIT 接口，状态机零改动。**设计要为业务演进预留位置。**

### 14. 工单创建的事务里，为什么事件要在"事务提交后"发布？

【参考答案】
事务提交前发布：异步消费者可能在事务回滚后收到事件，读到不存在的工单；或者事务未提交就读到半成品数据（隔离级别下甚至读不到）。用 TransactionSynchronizationManager.registerSynchronization 注册 afterCommit 回调，提交成功才发布——异步任务拿到的永远是已提交的完整数据。**"先落库、后通知"，通知的时机和事务绑定。**

### 15. RESOLVED 和 CLOSED 为什么是两步？

【参考答案】
解决 = 客服认为搞定了；关闭 = 正式翻篇。两步之间留窗口期：客户可能回来确认/补充（REOPEN 重开处理），客服能复查。如果解决即关闭，客户回来就得从 CLOSED 重开（权限要求更高：ticket:assign），链路绕、体验差。

### 16. CANCELLED 为什么是终态？

【参考答案】
取消 = 作废，不允许复活：复活会破坏审计严肃性（作废的单被翻出来），也会制造状态混乱。客户要重新求助就创建新工单，语义干净。**终态设计要"狠心"，该断的链路要断干净。**

### 17. allowedEvents 返回给前端有什么好处？

【参考答案】
单一事实来源：前端按钮禁用逻辑不自己维护状态判断表，直接读后端 VO 的 allowedEvents 渲染——状态机改了前端自动联动，不会出现"前端和后端矩阵不一致"的经典问题。**后端不仅返回数据，还返回"操作能力"，是前后端契约化的体现。**

### 18. 状态机的测试怎么写的？覆盖了什么？

【参考答案】
StateMachineTest：遍历 23 条合法转移逐一断言 fire 结果正确；再断言 10+ 条非法组合（比如 CANCELLED 的所有事件、RESOLVED 的 REPLY）抛 IllegalTransitionException。**矩阵全量覆盖 + 非法路径覆盖，规则的正确性被测试锁定，而不是靠人眼检查。**

## 二、SLA 引擎与消息队列（19-36）

### 19. SLA 引擎的整体设计是什么？

【参考答案】
工单创建时按优先级匹配 SLA 策略，生成计时单（ticket_sla）并投递两条 RocketMQ 延迟消息（首次响应检查、解决检查，投递时间为截止时间戳）。消息到点被消费：检查对应指标是否达成——达成结算"按时"，未达成标记"超时"并升级（状态机 TIMEOUT_ESCALATE → ESCALATED）。同时补偿扫描每 5 分钟兜底：找出"未升级、未结算、已过截止"的计时单，复用同一套结算逻辑补处理。**延迟消息保证准时，补偿扫描保证不漏。**

### 20. 为什么"延迟消息 + 补偿扫描"缺一不可？

【参考答案】
延迟消息的弱点：可能丢失（broker 故障、消费失败重试耗尽）——丢了就没人检查了；补偿扫描的弱点：粒度粗（5 分钟）——只靠扫描，超时结算最多误差 5 分钟。两者互补：**延迟消息是"准时性"担当（毫秒级结算），扫描是"可靠性"担当（最终一定处理）**。单用任何一个都有致命缺陷。

### 21. 延迟消息是怎么实现的？RocketMQ 4.x 和 5.x 有什么区别？

【参考答案】
5.x 用 message.setDeliverTimeMs(绝对毫秒时间戳)，底层 broker 时间轮实现，支持任意延迟时长；4.x 只有 18 个固定延迟等级（1s/5s/10s/.../2h），无法精确到任意分钟。本项目 SLA 截止时间是策略动态算的，必须 5.x。前置条件：broker.conf 必须 enableScheduleMessage=true（默认关闭，否则消息立即投递）。

### 22. 延迟消息消费的幂等怎么做的？

【参考答案】
三层：① 消费前查 ticket_sla 的 escalation_triggered，已升级直接忽略；② 检查结算状态——已响应/已解决则结算"按时"返回；③ 升级动作里再查一次 escalation_triggered（先标记后动作）。消息重复投递 10 次效果等于 1 次。**幂等的核心：执行前查"是不是已经做过了"，执行时"先置标记再干活"。**

### 23. 延迟消息丢了会怎样？补偿扫描怎么兜底？

【参考答案】
最坏情况晚一个扫描周期（≤5 分钟）升级，不会永久漏掉。扫描查询条件：escalation_triggered=0 AND 未结算 AND 截止时间已过——不管消息丢没丢，只看数据库事实，把漏掉的构造为同构消息复用 handleDelayCheck 处理。**消息可以丢，事实（计时单）不丢，扫描按事实兜底。**

### 24. 消息和扫描同时触发升级怎么办？

【参考答案】
不会重复升级：escalate() 第一行检查 escalation_triggered 已置 1 则返回；两条触发路径（消息消费、补偿扫描）最终都走同一套逻辑，谁先到谁执行，后到的看见标记就退出。审计日志也只写一条。**"先置标记后执行动作"的防重设计保证并发触发安全。**

### 25. "先落库后发消息"是什么意思？为什么？

【参考答案】
createTicketSla 里：先 INSERT ticket_sla（落库），再投延迟消息。顺序反过来的问题：消息 2 小时后到达，消费时查不到计时单（事务未提交或已回滚）——结算失效，工单从此无 SLA 保障。先落库后发消息 + 发送失败不抛异常 + 扫描兜底：**数据在，SLA 就在。**

### 26. 发送延迟消息失败为什么不抛异常？

【参考答案】
因为发送失败不是致命错误：计时单已落库，补偿扫描 5 分钟内必然发现并处理——最终一致性有保障。如果抛异常，创建工单的主事务会跟着失败（客户连工单都建不了）——**MQ 故障不能传导到主流程，这是"MQ 是辅助设施"的定位决定的。**

### 27. SLA 的"按时/超时"怎么结算？响应了还会被记超时吗？

【参考答案】
结算依据是不可变事实字段：first_responded_at（首次回复时 transition 同一条 UPDATE 写入）、resolved_at。延迟消息到达时：有事实 → 结算按时（1）；无事实 → 结算超时（2）并升级。关键规则：**已经超时才响应不会翻盘**——承诺的是"截止前响应"，晚了就是晚了，超时记录保持 2。这个规则保证 SLA 统计（按时率）数据严肃可信。

### 28. 结算为什么不看工单状态，而看时间戳字段？

【参考答案】
状态是可变的（处理中 → 等待客户 → 处理中），时间戳是不可变事实（写入后不覆盖）。结算必须基于不可变事实——比如工单当前是 PROCESSING 不代表它响应过（可能是重开的）；但 first_responded_at 有值就一定是首次响应过。**统计和结算永远基于不可变事实，这是数据可信的根基。**

### 29. 升级是怎么触发状态机的？

【参考答案】
SLA 服务不直接调工单服务，发布 SlaTimeoutEvent（Spring 事件）→ TicketServiceImpl 的 @EventListener 方法消费 → transition(ticketId, TIMEOUT_ESCALATE, null, "SYSTEM")。解耦效果：两个模块互不知道对方存在（避免循环依赖）；未来升级动作增加（通知组长）只需加监听器。**边界情况：工单当前状态不允许超时升级（如已解决）→ transition 抛 ILLEGAL_TRANSITION 被吞掉——状态机是最后防线。**

### 30. 补偿扫描的查询为什么天然幂等？

【参考答案】
查询条件只选"未升级（escalation_triggered=0）、未结算（status=0）、已过截止"的记录；处理成功的记录要么置了升级标记、要么结算了状态——下次扫描永远不会再选中它们。**扫描可重复执行、可随时中断续跑，无副作用。**

### 31. 为什么补偿周期是 5 分钟？可以调整吗？

【参考答案】
cron 表达式配置化（app.sla.compensation-cron，默认 0 */5 * * * ?）：延迟消息正常工作时扫描只是兜底，5 分钟够；业务要更严（紧急单 1 分钟内升级）就把 cron 调密。**成本权衡：扫描越密，DB 查询越频繁；准点性由延迟消息保证，扫描不追求准点。**

### 32. SLA 消息体（SlaMessage）为什么带 slaId？

【参考答案】
slaId 是定位计时单的钥匙——消费时直接按 id 查实例，检查 escalation_triggered 和结算状态。消息体只承载"谁、查什么"（ticketId、slaId、checkType），所有判断依据都在数据库——**消息是提醒，数据库是事实**。即使消息内容被重建/篡改，消费逻辑依然安全。

### 33. SLA 策略匹配不到怎么办？

【参考答案】
按优先级 + status=1 精确匹配；匹配不到（策略被禁用/未配置）→ log.warn 跳过计时——工单照常流转，只是没有 SLA 保障。**降级容忍：配置缺失不卡死业务**，和 AI 降级同一哲学。

### 34. ticket_sla 的索引为什么这么建？

【参考答案】
uk_ticket_id（一单一份实例）+ idx_deadline_status(first_response_deadline, escalation_triggered)——后者精确匹配补偿扫描的两条查询（按响应截止扫、按解决截止扫）的"时间范围 + 状态过滤"最左前缀。**索引为查询服务，不是装饰。**

### 35. 如果消息提前投递了（时钟偏差），会误升级吗？

【参考答案】
不会。消费逻辑不看"当前时间 vs 投递时间"，只看业务事实（有没有响应/解决）。提前投递最坏只是提前几秒结算，结论不变（该升级还是升级，该按时还是按时）。**结算逻辑不依赖时间比对，只依赖事实判断——天然免疫时钟问题。**

### 36. SLA 相关的测试怎么写的？

【参考答案】
SlaServiceImplTest：mock 策略/计时单/生产者——验证已响应 → 消息到达结算按时不升级；未响应 → 超时置 2 且升级；escalation_triggered=1 后重复触发被忽略；补偿扫描构造消息复用 handleDelayCheck。M3 里程碑还做了真实端到端验证（1 分钟策略实测）。**单测覆盖分支，实测覆盖链路。**

## 三、并发与分布式锁（37-47）

### 37. 两个坐席同时抢同一张工单，会发生什么？

【参考答案】
第一个拿到 Redisson 锁（tryLock 等待 3s、租约 10s），锁内执行乐观锁 UPDATE（WHERE id + status=待分派 + version + agent_id IS NULL），成功；第二个等锁释放后执行同样的 UPDATE，WHERE 条件不匹配（status 已变或 agent_id 非空），影响 0 行抛 CONCURRENT_MODIFY。10 线程并发测试验证恰好 1 成功 9 失败。

### 38. 抢单的 UPDATE 为什么带 status 和 version 两个条件？agent_id IS NULL 是干嘛的？

【参考答案】
version 防"基于过期数据更新"（经典乐观锁）；status=待分派 是业务条件——管理员刚手动分派了，状态已变，抢不了；agent_id IS NULL 是语义兜底——已有人认领的工单不能再被领。**三个条件把"读到的状态不可信"这件事堵死：任何并发路径下最多一个更新成功。**

### 39. 分布式锁和乐观锁是冗余吗？能只留一个吗？

【参考答案】
不是冗余，是两道不同防线：分布式锁把并发请求串行化——1000 个抢单请求只有 1 个真正打到数据库做 UPDATE，其余在锁外失败返回，保护数据库；乐观锁是最终一致性兜底——锁会过期（租约 10s）、Redis 可能故障，CAS 保证无论如何最多一个成功。**锁挡流量，乐观锁保正确。**

### 40. tryLock(3, 10, SECONDS) 参数什么意思？锁过期了怎么办？

【参考答案】
等待 3 秒拿锁（拿不到直接失败返回，不无限等），拿到后锁 10 秒自动释放（防止持有者宕机死锁）。锁过期后的极端场景：第二个坐席拿到过期后的锁进来执行 UPDATE——乐观锁兜底：第一人的 UPDATE 已把 version+1，第二人的 WHERE version=旧值 匹配 0 行失败。**最坏结果：多打了一次数据库，业务不出错。**

### 41. Redisson 锁的 key 粒度怎么设计？为什么？

【参考答案】
`ticket:claim:{ticketId}`——锁的粒度是"一张工单"：不同工单的抢单互不阻塞，吞吐最大化。如果 key 设计成全局一个，所有工单的抢单都串行排队，性能就毁了。**锁的粒度 = 资源的粒度，锁得越细并发越高。**

### 42. 如果 Redis 挂了，抢单功能会怎样？会有脏数据吗？

【参考答案】
tryLock 抛异常/超时 → 抢单接口暂时不可用（提示稍后重试）——但不会有脏数据：即使有人绕过锁直接执行，乐观锁的 CAS 依然保证一致性。**正确性靠数据库，Redis 只是性能优化**——这是"Redis 是辅助设施"架构的直接收益。管理员手动分派不受影响（不走锁）。

### 43. 为什么用 SQL 的 setSql("current_load = current_load + 1") 而不是"读-加-写"？

【参考答案】
读-加-写三步有竞态：两个请求同时读到 3，都 +1 写成 4（真实应该是 5）——经典的丢失更新。SQL 原子自增把"读和写合成一步"，数据库保证原子性，永远不会丢更新。**能在 SQL 里原子完成的操作，绝不在代码里拆开做。**

### 44. 并发测试怎么写的？验证了什么？

【参考答案】
TicketClaimConcurrentTest：准备一张待分派工单 + mock 依赖，10 个线程同时执行 claim，断言恰好 1 个成功、9 个抛 CONCURRENT_MODIFY，且最终 agent_id 正确、状态日志只有一条 CLAIM。**并发正确性是"断言出来"的，不是"看起来没问题"。**

### 45. 为什么不用数据库行锁（SELECT ... FOR UPDATE）？

【参考答案】
行锁也能实现互斥，但：① 要开事务并持有锁到事务结束，锁持有时间长；② 热点行竞争下所有请求在数据库排队，数据库连接被占满的风险更高；③ 锁由数据库承担，扩展性差。抢单这种"竞争激烈但单次操作极快"的场景，Redis 锁 + 乐观锁更优。**不同并发方案适用不同场景，选型要讲场景。**

### 46. current_load 会不会不准？怎么改进？

【参考答案】
当前维护点：抢单 +1、关闭 -1。边缘场景（工单重派、取消）没有对旧坐席 -1——这是已知简化。改进：重派时对旧坐席 -1；或者更彻底，不冗余、分派时实时 COUNT 在途工单（慢但准）。**主动说出边界和方案，比被问住好一百倍。**

### 47. 什么是"条件更新"？项目里用在哪？

【参考答案】
条件更新 = 把判断条件写进 UPDATE 的 WHERE，数据库在一条语句内原子完成"检查 + 修改"。项目里用在：抢单（WHERE status=待分派 AND version=? AND agent_id IS NULL）、状态流转（WHERE version=? AND status=当前状态）。**这是消除"先读后写"竞态的标准武器——判断和修改不可分割。**

## 四、分派策略（48-55）

### 48. 四种分派策略分别怎么实现？

【参考答案】
轮询：Redis INCR 计数 % 在线坐席数（原子取模轮流）；负载最低：在线坐席按 current_load 升序取第一个（谁闲给谁）；技能匹配：工单 category 命中坐席 skill_tags（JSON 数组）则选他；AI 推荐：调 LLM 输出 {agentId, reason}，不可用或返回 null 就返回 null 交给下个策略。

### 49. 策略工厂的执行逻辑？

【参考答案】
查配置表 enabled=1 的策略按 weight 降序排，逐个执行 dispatch(ticket)，第一个返回非 null 的生效并记录 DispatchResult(agentId, strategy)；全部失败返回 null——工单保持待分派，由抢单和人工分派兜底。**自动分派是尽力而为的优化，人工兜底永远存在。**

### 50. 为什么策略的优先级和启停放数据库配置？

【参考答案】
运营可调：改 weight/enabled 一行数据立即生效，不用发版——比如 AI 服务稳定了，把 AI_RECOMMEND enabled 改 1、weight 调高。策略**实现**在代码（策略模式），策略**选择**在配置（表驱动），职责分离。**配置驱动让分派行为可热调整、可观测。**

### 51. 为什么自动分派是异步的？

【参考答案】
创建接口要快速响应客户；分派要查配置、查坐席、可能调 LLM（最慢 15s）——同步做会拖死创建链路。异步后：客户先拿到工单号，分派后台悄悄完成；分派失败也不影响创建成功（保持待分派 + 抢单兜底）。**异步边界 = 不阻塞主流程 + 失败隔离。**

### 52. AI 分派挂了会阻塞分派吗？

【参考答案】
不会。AiRecommendStrategy 内部 catch 所有异常返回 null（LLM 不可用、超时、解析失败都算"未命中"），工厂继续尝试下一个策略。即使 AI_RECOMMEND 权重最高且启用，失败也只是当没匹配到。**AI 是分派链路的锦上添花，不是必经之路。**

### 53. assign_strategy 字段有什么用？

【参考答案】
记录实际生效的策略编码。可观测性：运营统计各策略命中率、排查分派问题、评估 AI 推荐质量。**成本一行字段，价值长期——先埋点再分析。**

### 54. 分派和 AI 分类都监听创建事件，会不会互相干扰？

【参考答案】
不会。两个 @Async 监听器独立执行：分类写 ai_* 建议字段，分派读的是正式 category——分派时 category 可能还是 null（分类未完成），技能匹配策略自然 miss 走下一策略。**链路解耦 + 各自降级：分派不依赖 AI 结果，依赖不到就降级，这是"AI 只做增强"的落地。**

### 55. 分派成功后的状态流转怎么做的？

【参考答案】
transition(ticketId, AUTO_ASSIGN, null, "SYSTEM", agentId, groupId, strategy)——SYSTEM 事件（不校验用户权限，只系统内部触发），同一条 UPDATE 完成：状态 2→3、写 agent_id/group_id、记 assign_strategy。**一条 SQL 原子完成"状态 + 归属 + 策略记录"。**
