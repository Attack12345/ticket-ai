## 2.1 先补数据库基础（15 分钟速成）

### 2.1.1 表 = Excel 表格

数据库里的"表"（Table）就是一张 Excel 表：**列**是字段（Field/Column），**行**是一条记录（Record）。

```sql
CREATE TABLE `sys_user` (
  `id`          bigint unsigned NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `username`    varchar(50)  NOT NULL COMMENT '登录名',
  `password`    varchar(100) NOT NULL COMMENT 'BCrypt 密码',
  ...
);
```

逐词翻译：
- `id bigint unsigned NOT NULL AUTO_INCREMENT`：id 这一列，类型是"无符号大整数"，**不允许为空**，**自动增长**（每插一行自动 +1）。
- `varchar(50)`：最长 50 个字符的字符串。
- `NOT NULL`：这一列必须有值，不能留空。
- `DEFAULT 1`：不填时默认给 1。
- `COMMENT 'xxx'`：注释，说明这一列是干嘛的（项目要求每个字段必须写注释）。
- `PRIMARY KEY (id)`：主键，唯一标识一行，自动建索引。
- `UNIQUE KEY uk_username (username)`：唯一键——username 列的值全表不允许重复，重复插入直接报错。
- `KEY idx_status (status)`：普通索引，给查询加速。

### 2.1.2 三个"键"的直觉

| 概念 | 直觉 | 类比 |
|---|---|---|
| 主键 PRIMARY KEY | 每行的身份证号，唯一且必有 | 学号 |
| 唯一键 UNIQUE KEY | 某些列的值不许重复（可以有多个唯一键） | 身份证号 + 手机号都不能重 |
| 索引 INDEX | 给某列建"目录"，查询变快 | 书末的索引页 |

**为什么不能全表都加索引？** 索引是额外存储 + 每次写入都要更新，索引太多写入变慢。所以**只给"经常用来查询和筛选"的列建索引**。

### 2.1.3 逻辑删除 vs 物理删除

- **物理删除**：`DELETE FROM ticket WHERE id=1`——记录真的没了，查不到也恢复不了。
- **逻辑删除**：`UPDATE ticket SET deleted=1 WHERE id=1`——记录还在，只是被打上"已删除"标记，查询时自动过滤掉 `deleted=0` 的。

本项目用 MyBatis-Plus 框架，配置了 `logic-delete-field: deleted`，之后框架自动把删除变成 UPDATE、查询自动加 `deleted=0` 条件——**对代码完全透明**。

**为什么用逻辑删除？** 工单、知识库这种业务数据，误删了要能恢复；而且历史数据可能还有统计价值。但注意：**有些表绝对不能删**（状态日志、审计日志），我们 2.9 讲。

### 2.1.4 事务（Transaction）

"要么全成功，要么全失败"的一组操作。比如转账：A 扣钱 + B 加钱必须一起成功。本项目：改工单状态 + 写状态日志 必须一起成功。

## 2.3 权限组：为什么拆成 5 张表？（RBAC 模型）

### 2.3.1 直觉问题

公司有 3 个角色：管理员、客服组长、普通客服。有 11 种操作：查看工单、领取工单、回复工单、管理 SLA 策略……

如果设计成 `sys_user` 表里加一列 `role='管理员'`，会怎样？
- 某天"查看工单"这个权限要从管理员身上拿掉？→ 你得改代码。
- 客服组长和普通客服差 2 个权限，其余一样？→ 角色定义越来越乱。

**答案：把"权限"从"角色"里拆出来，用三张主表 + 两张关联表**：

```
sys_user（用户）         张三
  │
  ▼ 通过 sys_user_role 关联
sys_role（角色）          管理员
  │
  ▼ 通过 sys_role_permission 关联
sys_permission（权限）    ticket:claim（领取工单）
```

查"张三能干什么"的路径：张三 → 找他的角色 → 找角色的权限 → 得到权限码列表。

### 2.3.2 五张表逐个看

**sys_user 用户表**：id、username（唯一键，不能重名）、password（存 BCrypt 哈希，不是明文）、nickname、phone、status（0 禁用 1 启用）、创建/更新人、deleted。

**sys_role 角色表**：id、name、code（唯一键，如 ADMIN/AGENT）、status。**角色就是"权限的集合"，code 是它的名字**。

**sys_permission 权限表**：id、code（唯一键）、name、type（MENU 菜单 / BUTTON 按钮）、parent_id（父子层级，本项目都挂 0 根下）。

权限码长这样：`ticket:view`、`ticket:claim`、`ticket:reply`…… 格式是"资源:操作"，像 `ticket:claim` = "对工单做领取操作"。共 11 个。

**sys_user_role 用户-角色关联表**：就两列 user_id + role_id + 联合唯一键 (user_id, role_id)——**一个用户可以有多个角色**（张三既是管理员也是客服）。

**sys_role_permission 角色-权限关联表**：role_id + permission_id + 联合唯一键——**一个角色有一堆权限**。

### 2.3.3 为什么"关联表"是必要的

"用户-角色-权限"是**多对多**关系：一个用户多个角色，一个角色多个用户。存一张表里塞不下；塞两列（逗号分隔）查询起来痛苦。**标准解法：中间关联表**。这也是数据库设计的通用套路，后面技能组也是这个模式（一次学会，两处用上）。

## 2.4 渠道组：message_no 是整组表的心脏

### 2.4.1 为什么要"渠道"表

客户从哪进来？网页表单（WEB_API）、邮件（EMAIL）。每个渠道的配置不同（邮件要配 IMAP 服务器地址），所以建一张 `channel` 表登记渠道：code（唯一键：WEB_API/EMAIL）、name、config_json（JSON 配置，如邮件参数）、status（启停）。

### 2.4.2 channel_message：消息原件 + 幂等键

客户提交问题时，渠道会先把"原始消息"存档：客户名、联系方式、标题、内容、**原始报文 raw_json**（渠道原样返回的完整数据，排查问题时有用）。

这张表最重要的字段：**message_no（渠道消息号）有唯一键**。

### 2.4.3 什么是"幂等"？为什么它是心脏？

场景：客户网络不好，点提交没反应，又点了一次——两条一模一样的请求到达服务器。

如果没有幂等机制：系统建了两张一模一样的工单，客户被处理两遍，客服一脸懵。

有了 `message_no` 唯一键：第二条请求插入时，数据库直接报"message_no 重复"——代码捕获这个错误，去查"这个 message_no 对应的工单"，**直接返回那张旧工单**。结果：请求发了两次，工单只有一张，返回结果一样。

**这就是幂等：同一操作做多少次，效果都等于做一次。** 面试高频概念，后面还会遇到（消息消费、AI 调用都是这个思想）。

## 2.5 工单组：ticket 主表逐字段拆解（核心中的核心）

### 2.5.1 ticket 表 —— 工单一生的档案

我们把字段按"职责"分组看：

**① 身份字段**：id（主键）、ticket_no（工单号，唯一键）。工单号长这样：`T202608180001`——"T" + 日期 + 6 位序列，由 Redis 计数生成（第 5 篇讲为什么用 Redis）。

**② 内容字段**：title（标题）、description（描述）、category（最终分类：售后/售前/投诉…）、priority（优先级 1-4，默认 3 中等）。

**③ 状态字段**：status（8 个状态值，默认 2 待分派）、version（乐观锁版本号，第 5 篇细讲）。

**④ 归属字段**：channel_id（来自哪个渠道）、agent_id（当前处理客服）、group_id（技能组）、assign_strategy（实际用了哪个分派策略——可观测性：运营能统计哪种策略分派了多少单）。

**⑤ SLA 字段**：sla_policy_id（用了哪个策略）、first_response_deadline（首次响应截止时间）、resolve_deadline（解决截止时间）、first_responded_at（实际首次响应时间）、resolved_at（实际解决时间）、closed_at（关闭时间）。
> 注意：这些时间和 ticket_sla 表里是**重复**的！为什么？2.9 讲"冗余"。

**⑥ AI 建议字段**：ai_category（AI 建议的分类）、ai_priority（AI 建议的优先级）、ai_score（AI 的置信度 0-1）。
> 注意：AI 结果存在"建议字段"，**不直接覆盖**正式字段 category/priority。客服点"采纳"后才会同步过去。**AI 永远不做最终决定**——这个设计后面反复出现。

**⑦ 通用字段**：create_by/update_by（谁建的/谁改的）、create_time/update_time、deleted（逻辑删除）、remark。

**索引设计**：`uk_ticket_no`（工单号唯一）、`idx_status_priority_create(status, priority, create_time)`（按状态+优先级+时间筛选，看板/列表的主力查询）、`idx_agent_id`（查某客服的工单）、`idx_category`（按分类筛选）。

### 2.5.2 ticket_status_log —— 状态流水账，打死不能删

每一张工单的**每一次状态变化**，都在这张表追加一行：from_status（从哪来）、to_status（到哪去）、event（什么事件触发的）、operator_id（谁操作的，系统事件为 NULL）、operator_type（USER 人操作 / SYSTEM 系统操作）。

**为什么这么重要？**
1. 出了纠纷能还原真相："这张单 3 天没人管"——查日志：创建后一直待分派，超时后系统自动升级。
2. 审计需求：谁改的状态，改了哪一步。
3. 所以设计上它是"事件流"：**只增不删**，没有 deleted 字段，也没有 UPDATE 的需求。

面试延伸：这种表叫**事件溯源（Event Sourcing）**思想的简化版——不记"当前状态"，而是记"发生了什么"，当前状态可以由事件推导出来。

### 2.5.3 ticket_comment —— 回复与内部备注

type：REPLY（回复客户）/ INTERNAL（内部备注，客户看不到）；visibility：ALL（客户可见）/ INTERNAL（仅内部）。

一张工单的沟通记录：客服回客户的、客户回的、客服之间留的内部小纸条，都在这。回复操作还会触发状态变化（处理中 → 等待客户），这是状态机的事（第 3 篇）。

## 2.6 保障组：策略 vs 实例，SLA 的核心概念

### 2.6.1 sla_policy —— 策略是"规则模板"

公司规定：**紧急工单** 15 分钟内首次响应、4 小时解决；**高优先级** 1 小时/8 小时；**中** 2 小时/24 小时；**低** 8 小时/48 小时且不自动升级。

这就是 4 条"策略"，每条一行：
- priority（适用哪个优先级，唯一键：每个优先级只能有一个策略）
- first_response_minutes（首次响应时限，分钟）
- resolve_minutes（解决时限，分钟）
- auto_escalate（超时是否自动升级）
- escalate_action（升级后做什么，JSON：如通知哪个组）

**这是"模板"，不是"某张工单的实际承诺"**——就像合同模板 vs 签了字的那份合同。

### 2.6.2 ticket_sla —— 实例是"每张工单的计时单"

工单创建时，系统按优先级找到策略，**算好截止时间，生成一份计时单**：

- ticket_id（哪张工单，唯一键：一单一份）
- first_response_deadline（首次响应截止 = 创建时间 + 策略分钟数）
- resolve_deadline（解决截止）
- first_response_status / resolve_status（0 未到期 / 1 按时 / 2 超时）
- escalation_triggered（是否已升级——**这个字段是第 4 篇的命根子**，先记住）
- escalated_at（升级时间）

**为什么策略和实例要分两张表？** 策略可以改（明天把中优先级从 2 小时改成 3 小时），但**已创建工单的承诺不能变**（客户按旧承诺投诉，你得说得清）。实例表把"当时算好的截止时间"固化下来，策略怎么改都影响不了历史工单。

### 2.6.3 dispatch_strategy —— 分派策略配置

就 4 行数据：strategy_type（ROUND_ROBIN 轮询 / LEAST_LOADED 负载最低 / SKILL_MATCH 技能匹配 / AI_RECOMMEND AI 推荐）、weight（权重，按权重降序尝试）、enabled（启停）。

**为什么放数据库不放代码？** 运营想改优先级，改一行数据就行，不用发版。比如 AI 分派默认关着，某天想开：enabled 改 1 即可。（第 5 篇细讲）

## 2.7 坐席组：人、组、关系

- **agent（坐席）**：user_id（关联登录账号，唯一键）、name、status（0 离线 1 在线）、**current_load（当前负载数——正在处理+等待客户的工单数，用来"谁闲给谁"）**、**skill_tags（技能标签，JSON 数组字符串：["售后","投诉"]，用来技能匹配）**。
- **skill_group（技能组）**：name、description、status。比如"售后组""投诉组"。
- **skill_group_agent（关联表）**：group_id + agent_id + 联合唯一键。一个坐席可以属于多个组。

又是"多对多 + 关联表"——和 RBAC 一样的套路，看到关联表就秒懂。

**current_load 为什么要存表里而不是每次现算？** 现算 = 每次分派都要 COUNT 一次所有在途工单，慢。存表里 = 抢单成功时 +1、关闭时 -1（SQL 原子自增），查的时候直接读。**用可控的冗余换速度**，代价是维护点必须收敛（只有两处改它）。这个"冗余 vs 一致性"的权衡面试官很喜欢问。

## 2.8 内容组：知识库、审计、AI 用量

### 2.8.1 knowledge_base + kb_segment —— 文章和它的"切片"

knowledge_base（文章）：title、category、content（正文）、status（上架/下架）、view_count（浏览数）、author_id。

kb_segment（分段）：**一篇文章会被切成若干"段"**——kb_id（哪篇文章）、seq（第几段）、content（段内容）、char_count（字数）。

**为什么要切段？** 给 LLM 当参考资料时，整篇文章太长（token 费钱且超出上下文窗口），切成 500 字左右的段，搜的时候只取最相关的几段。切法：按 Markdown 标题层级切，没有标题的按 500 字定长滑动窗口切、**重叠 50 字**（防止一句话被拦腰切断）。这是第 6 篇 RAG 的关键细节。

**关键设计：段的内容（向量）存在哪？** MySQL 存元数据，**向量存在 ES**。为什么？MySQL 不会算"哪段和这段话意思最接近"（向量相似度计算是 ES 的强项），而且向量丢了可以从文章重新生成。**MySQL 是事实源，ES 是可重建的索引**——第 1 篇那句话又来了。

### 2.8.2 audit_log —— 审计日志（谁干的，记下来）

敏感操作必须留痕：user_id、username、action（如 TICKET_ASSIGN 分派工单）、target_type/target_id（对哪个对象）、detail_json（详情）、ip（操作者 IP）。

**和 ticket_status_log 的区别**：状态日志只管"状态变化"；审计日志管"一切敏感操作"（分派、关闭、升级、取消、改 SLA 策略、系统超时升级都记）。两者都只增不删。

### 2.8.3 ai_usage_log —— LLM 调用账本

每次调用 LLM（不管成功失败）记一行：ticket_id、scene（场景：CLASSIFY 分类 / SUGGEST 建议 / DISPATCH 分派 / EMBED 向量化）、model（用的哪个模型）、三个 token 数（输入/输出/总量——**token 就是钱**）、latency_ms（耗时）、success（成功没）、error_msg（失败原因）。

**为什么记这个？** 月底算账（这个月 AI 花了多少钱）、监控质量（失败率、平均耗时）、排查问题（哪次调用失败了）。**AI 可观测 = AI 工程化**，这是"调了个 API"和"做了 AI 功能"的分水岭。

## 2.9 三个"表设计智慧"总结（面试亮点）

**智慧一：可控冗余，换查询速度**
ticket 表冗余了 SLA 截止时间（ticket_sla 里也有）、agent 冗余了 current_load。代价是写的时候要多维护，收益是列表页不用联表。**前提：冗余字段的维护点必须收敛**——deadline 只在状态变更时更新，current_load 只在抢单/关闭时更新。

**智慧二：幂等键（唯一键）是最可靠的防重**
message_no 唯一键。靠代码检查"有没有重复"有并发窗口（两个请求同时查，都没查到，都插入）；靠数据库唯一键，第二个插入必然失败。**数据库约束是最后防线**。

**智慧三：审计数据只增不删**
ticket_status_log / audit_log / ai_usage_log 三个表没有 deleted 字段、没有 UPDATE 需求——它们是"流水账"，账本不能撕页。业务数据（工单/坐席/知识库）用逻辑删除，方便恢复；流水账物理保留，保证可追溯。

## 2.10 本篇小结

- 20 张表分 6 组：权限组（RBAC 五表）、渠道组（幂等键）、工单组（ticket + 流水账 + 评论）、保障组（SLA 策略/实例 + 分派配置）、坐席组（人组关系）、内容组（知识库 + 双日志）。
- 三大套路：**多对多 → 关联表**（出现两次）、**策略模板 vs 实例**（SLA 两张表）、**事实源 + 可重建索引**（MySQL + ES）。
- 三个智慧：可控冗余、幂等键、流水账不删。
