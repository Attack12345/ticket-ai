## 3.1 先用生活例子理解"状态机"

### 3.1.1 红灯变绿灯，为什么不能直接跳？

红绿灯有 3 种状态：红灯、黄灯、绿灯。它有规矩：

```
红灯 ──等待──► 绿灯 ──等待──► 黄灯 ──等待──► 红灯
```

红灯**只能**变绿灯，不能直接变黄灯——因为"红灯直接跳黄灯"会让司机和行人都懵掉。

这个"**状态 + 规则**"的组合，就是状态机（State Machine）：
- **状态（State）**：当前是什么情况（红灯/绿灯/黄灯）
- **事件（Event）**：发生了什么（时间到）
- **转移（Transition）**：某个状态下发生某个事件 → 变成什么状态（红灯 + 时间到 → 绿灯）
- **合法转移表**：哪些"状态+事件"组合是允许的，其余的**一律拒绝**

### 3.1.2 外卖订单的状态机

你点的外卖，订单状态：已下单 → 商家接单 → 骑手取餐 → 配送中 → 已送达。规矩：
- "已送达"的订单不能再变回"商家接单"（除非用户投诉重下，那是新订单）。
- "已下单"可以取消，"配送中"不能随便取消（要联系客服）。

外卖平台每天上亿订单，全靠状态机管着——**不是代码里 if-else 乱写，而是一张规则表**。

### 3.1.3 为什么工单必须用状态机？

没有状态机的世界（if-else 乱写）：
- 客服 A 把"已关闭"的工单改回"处理中"，客服 B 又改回"已关闭"，状态乱飞，没人说得清发生了什么。
- 客户投诉"为什么我的单子突然升级了"，查无记录。
- 操作权限失控：普通客服点了"分派"按钮也能分派。

有状态机的世界：
- 所有状态变化**必须经过一张规则表**校验，非法变化直接报错。
- 每次变化**自动写一条流水账**（ticket_status_log），真相永远可查。
- 每个变化**自带权限要求**，权限不够直接拒绝。

**状态机 = 业务规矩的代码化。**

## 3.2 项目的 8 个状态：每个都是业务语言

| code | 状态 | 大白话含义 |
|---|---|---|
| 1 | NEW | 新建（草稿，还没正式提交） |
| 2 | PENDING_ASSIGN | 待分派（工单建好了，等人来领） |
| 3 | PROCESSING | 处理中（客服正在处理） |
| 4 | WAITING_CUSTOMER | 等待客户（问了客户问题，等客户回复） |
| 5 | RESOLVED | 已解决（客服认为解决了，等待关闭） |
| 6 | CLOSED | 已关闭（这事翻篇了） |
| 7 | ESCALATED | 已升级（超时了/搞不定了，上报处理） |
| 8 | CANCELLED | 已取消（不用处理了） |

**怎么记住？** 它其实是一条业务线的 8 个阶段，加上两个分支：

```
主流程： 新建 → 待分派 → 处理中 → 等待客户 → 已解决 → 已关闭
                                  ↑____↓（客户回复回到处理中）
分支1：任何"干活"阶段超时 → 已升级（ESCALATED）
分支2：处理前/处理中 不想干了 → 已取消（CANCELLED，终态）
```

## 3.3 项目的 12 个事件：每个都对应一个"动作"

| 事件 | 谁触发 | 业务含义 |
|---|---|---|
| SUBMIT | 用户 | 提交草稿 |
| AUTO_ASSIGN | 系统 | 自动分派成功 |
| MANUAL_ASSIGN | 管理员 | 手动指定给某客服 |
| CLAIM | 坐席 | 抢单领取 |
| REPLY | 坐席 | 回复客户 |
| CUSTOMER_REPLY | 系统 | 客户来信了 |
| RESOLVE | 坐席/管理员 | 标记解决 |
| CLOSE | 坐席/管理员 | 关闭 |
| REOPEN | 坐席/管理员 | 重开（客户又回来了） |
| ESCALATE | 坐席/管理员 | 人工升级（搞不定，上报） |
| TIMEOUT_ESCALATE | 系统 | SLA 超时，系统自动升级 |
| CANCEL | 创建人/管理员 | 取消 |

**注意三类触发者**：
- **用户/坐席/管理员**：人在页面上点的按钮。
- **系统（SYSTEM）**：AUTO_ASSIGN（自动分派）、CUSTOMER_REPLY（客户来信）、TIMEOUT_ESCALATE（超时）——这三个没有按钮，是后台逻辑触发的。它们不需要"人"的权限，但**也没有任何 HTTP 接口能直接触发**，只能走系统内部链路。

## 3.4 23 条转移矩阵：权威规则表（要背）

**读法**：某状态 + 某事件 → 目标状态 + 需要的权限。权限列写"SYSTEM"表示仅系统内部可触发。

**NEW（2 条）**：
| 状态 | 事件 | 目标 | 权限 |
|---|---|---|---|
| NEW | SUBMIT | PENDING_ASSIGN | ticket:view |
| NEW | CANCEL | CANCELLED | ticket:view |

**PENDING_ASSIGN 待分派（6 条）**：
| 状态 | 事件 | 目标 | 权限 |
|---|---|---|---|
| PENDING_ASSIGN | AUTO_ASSIGN | PROCESSING | SYSTEM |
| PENDING_ASSIGN | MANUAL_ASSIGN | PROCESSING | ticket:assign |
| PENDING_ASSIGN | CLAIM | PROCESSING | ticket:claim |
| PENDING_ASSIGN | ESCALATE | ESCALATED | ticket:escalate |
| PENDING_ASSIGN | TIMEOUT_ESCALATE | ESCALATED | SYSTEM |
| PENDING_ASSIGN | CANCEL | CANCELLED | ticket:close |

**PROCESSING 处理中（5 条）**：
| 状态 | 事件 | 目标 | 权限 |
|---|---|---|---|
| PROCESSING | REPLY | WAITING_CUSTOMER | ticket:reply |
| PROCESSING | RESOLVE | RESOLVED | ticket:resolve |
| PROCESSING | ESCALATE | ESCALATED | ticket:escalate |
| PROCESSING | TIMEOUT_ESCALATE | ESCALATED | SYSTEM |
| PROCESSING | CANCEL | CANCELLED | ticket:close |

**WAITING_CUSTOMER 等待客户（4 条）**：
| 状态 | 事件 | 目标 | 权限 |
|---|---|---|---|
| WAITING_CUSTOMER | CUSTOMER_REPLY | PROCESSING | SYSTEM |
| WAITING_CUSTOMER | REPLY | WAITING_CUSTOMER | ticket:reply |
| WAITING_CUSTOMER | RESOLVE | RESOLVED | ticket:resolve |
| WAITING_CUSTOMER | TIMEOUT_ESCALATE | ESCALATED | SYSTEM |

**RESOLVED 已解决（2 条）**：
| 状态 | 事件 | 目标 | 权限 |
|---|---|---|---|
| RESOLVED | REOPEN | PROCESSING | ticket:resolve |
| RESOLVED | CLOSE | CLOSED | ticket:close |

**CLOSED 已关闭（1 条）**：
| 状态 | 事件 | 目标 | 权限 |
|---|---|---|---|
| CLOSED | REOPEN | PROCESSING | ticket:assign |

**ESCALATED 已升级（3 条）**：
| 状态 | 事件 | 目标 | 权限 |
|---|---|---|---|
| ESCALATED | MANUAL_ASSIGN | PROCESSING | ticket:assign |
| ESCALATED | RESOLVE | RESOLVED | ticket:resolve |
| ESCALATED | CANCEL | CANCELLED | ticket:close |

**CANCELLED**：终态，**没有任何出口**——取消的工单永远不能复活。

合计 2+6+5+4+2+1+3 = **23 条**。

**三处需要用心体会的设计**：

1. **WAITING_CUSTOMER --REPLY--> WAITING_CUSTOMER（自环）**：客服在等待客户时还可以继续回复（比如补充说明），状态不变但操作合法。自环 = "同状态下允许重复动作"。
2. **CLOSED --REOPEN--> PROCESSING**：已关闭的还能重开（客户又回来了）——但注意重开需要 ticket:assign 权限（比 RESOLVED 的 REOPEN 权限高），因为"把死单复活"是敏感操作。
3. **ESCALATED 只能通过 MANUAL_ASSIGN 回 PROCESSING**：升级后的工单必须有人工介入重新分派——系统不能自动把升级单又分出去（升级 = 需要人重视）。

## 3.5 代码走读：状态机 5 个类（约 200 行）

### 3.5.1 TicketStatus —— 状态枚举

```java
public enum TicketStatus {
    NEW(1, "新建"), PENDING_ASSIGN(2, "待分派"), PROCESSING(3, "处理中"),
    WAITING_CUSTOMER(4, "等待客户"), RESOLVED(5, "已解决"), CLOSED(6, "已关闭"),
    ESCALATED(7, "已升级"), CANCELLED(8, "已取消");
    private final int code;   // 对应数据库 tinyint 值
    private final String desc; // 中文含义
    // byCode(int) 静态方法：code → 枚举，给"从数据库读出数字"的代码用
}
```

枚举 = 一组固定的常量集合。数据库里存的是数字（2），代码里用枚举名（PENDING_ASSIGN），转换靠 byCode。

### 3.5.2 TicketEvent —— 事件枚举

```java
public enum TicketEvent { SUBMIT, AUTO_ASSIGN, MANUAL_ASSIGN, CLAIM, REPLY,
    CUSTOMER_REPLY, RESOLVE, CLOSE, REOPEN, ESCALATE, TIMEOUT_ESCALATE, CANCEL }
```

### 3.5.3 Transition —— 一条转移的"定义"

```java
public record Transition(TicketStatus from, TicketEvent event,
                         TicketStatus to, String requiredPermission) {
    public boolean isSystemOnly() {
        return "SYSTEM".equals(requiredPermission);
    }
}
```

record 是 Java 的"数据容器"写法（自动生成构造器/getter）。一条 Transition = 一行矩阵（从哪、什么事件、到哪、要什么权限）。

### 3.5.4 StateMachineRegistry —— 把 23 条矩阵"填"进内存

```java
public final class StateMachineRegistry {
    // 两层 Map：先按"当前状态"找，再按"事件"找 → 得到转移定义
    private static final Map<TicketStatus, Map<TicketEvent, Transition>> TRANSITIONS =
            new EnumMap<>(TicketStatus.class);

    static {  // 类加载时执行一次，把 23 条规则全部注册进去
        register(TicketStatus.NEW, TicketEvent.SUBMIT, TicketStatus.PENDING_ASSIGN, "ticket:view");
        register(TicketStatus.NEW, TicketEvent.CANCEL, TicketStatus.CANCELLED, "ticket:view");
        register(TicketStatus.PENDING_ASSIGN, TicketEvent.AUTO_ASSIGN, TicketStatus.PROCESSING, "SYSTEM");
        // ... 共 23 行，与 3.4 的表格一一对应
    }

    // 查询：找不到返回 null（表示非法组合）
    public static Transition find(TicketStatus from, TicketEvent event) { ... }
    // 查询：该状态允许的所有事件（前端按钮禁用靠它）
    public static Set<TicketEvent> allowedEvents(TicketStatus from) { ... }
}
```

**为什么用静态块，不用数据库配置？** 规则是"代码事实"——编译时写错就编译失败，git 能追溯谁改的，测试能全量断言。如果用数据库配置，规则改动了没有版本控制，出了生产事故都不知道哪次改的。**核心规则用代码固化，是工程上的刻意选择。**

**为什么用 EnumMap？** 枚举专用 Map，按枚举序号数组存储，访问最快、内存最省，比 HashMap 更合适。

### 3.5.5 StateMachine —— 引擎的门面（4 个静态方法）

```java
public final class StateMachine {
    public static boolean canTransition(TicketStatus from, TicketEvent event)
        // 问：这个组合合法吗？（查得到定义 = 合法）
    public static Transition getTransition(TicketStatus from, TicketEvent event)
        // 答：给定义（含权限要求）
    public static TicketStatus fire(TicketStatus from, TicketEvent event)
        // 执行：非法直接抛 IllegalTransitionException
    public static Set<TicketEvent> allowedEvents(TicketStatus from)
        // 问：这个状态现在能做哪些操作？
}
```

**整个状态机引擎不到 50 行代码**——因为规则全在注册表里，引擎只做"查表"。这提醒我们：**复杂的不是代码，是规则本身**。

## 3.6 核心方法走读：transition()（状态变更唯一入口）

代码位置：`TicketServiceImpl.transition(...)`。**全项目只有这一个方法能改工单状态**（抢单 claim 虽然单独实现了，但底层也是同一套"状态机校验 + 乐观锁"模式）。五步走：

```
transition(ticketId, event, ...)
│
├─ 第 1 步：查工单
│    SELECT * FROM ticket WHERE id = ?   → 不存在：抛"工单不存在"
│
├─ 第 2 步：状态机校验（合法性）
│    StateMachine.getTransition(当前状态, 事件)
│    → null：抛 ILLEGAL_TRANSITION "当前状态[X]不允许事件[Y]"
│    → 非 null：拿到这条转移的"目标状态 + 权限要求"
│
├─ 第 3 步：权限校验（谁能做）
│    如果这条转移要求权限（非 SYSTEM）：
│      从"当前登录用户"（UserContextHolder）取权限码列表
│      没有对应权限：抛 FORBIDDEN "缺少权限: ticket:claim"
│    （SYSTEM 事件跳过，因为只能系统内部触发）
│
├─ 第 4 步：乐观锁更新（并发安全，一条 SQL 干三件事）
│    UPDATE ticket
│      SET status = 目标状态,
│          version = version + 1,          ← 版本号 +1
│          [时间戳/归属字段，见 3.7]
│    WHERE id = ? AND version = ? AND status = 当前状态
│    → 影响 0 行：说明数据已被别人改过 → 抛 CONCURRENT_MODIFY
│
├─ 第 5 步：写状态流水账
│    INSERT INTO ticket_status_log(from, to, event, operator, ...)
│
└─ 特殊事件后置：RESOLVE 时发布"工单已解决"事件
     （异步把工单写进 ES，供 AI 召回，第 6 篇讲）
```

**第 4 步值得再想想**：为什么 UPDATE 要带 `AND version = ? AND status = 当前状态`？
- `version`：我读到的是版本 5，如果数据库里已经是版本 6，说明别人在我读和写之间改过了——我的修改基于过期数据，拒绝。
- `status`：业务条件兜底。比如我读到"待分派"，但管理员已经手动分派成"处理中"（version 恰好没变？不，分派也会 +1……但多一个条件多一层保险，比如未来的代码忘了 version）。
- 影响 0 行 = 抢不过别人 = 抛并发冲突错误，前端提示"数据已变，请刷新"。

**这一条 SQL 是"条件更新"（CAS）的教科书写法：把判断条件写进 UPDATE 的 WHERE，让数据库在一条语句内原子地完成"检查 + 修改"。**

## 3.7 事件后置动作：时间戳结算（细节里的功夫）

某些事件发生时，除了改状态，还要"顺便"记录业务时间点。设计上的硬性要求是：**后置动作和状态变更必须在同一条 UPDATE 里完成**（不能分两条 SQL）。看代码：

```java
UpdateWrapper<TicketDO> update = new UpdateWrapper<TicketDO>()
        .eq("id", ticketId)
        .eq("version", ticket.getVersion())
        .eq("status", from.getCode())
        .set("status", transition.to().getCode())
        .set("version", ticket.getVersion() + 1);
// 事件后置动作（并入同一条 UPDATE）：
if (event == TicketEvent.REPLY && ticket.getFirstRespondedAt() == null) {
    update.set("first_responded_at", now);        // 首次回复：记下首次响应时间
} else if (event == TicketEvent.RESOLVE) {
    update.set("resolved_at", now);                // 解决：记下解决时间
} else if (event == TicketEvent.CLOSE || event == TicketEvent.CANCEL) {
    update.set("closed_at", now);                  // 关闭/取消
} else if (event == TicketEvent.REOPEN) {
    update.set("resolved_at", null).set("closed_at", null);  // 重开：清掉旧时间
} else if (event == TicketEvent.AUTO_ASSIGN || event == TicketEvent.MANUAL_ASSIGN) {
    update.set("agent_id", agentId);               // 分派：写上归属人
    update.set("group_id", groupId);
    update.set("assign_strategy", assignStrategy); // 记下用哪个策略
}
```

**为什么必须一条 UPDATE？** 假设分两条 SQL（先改状态，再写时间戳）：
1. 两条 SQL 之间有其他请求插进来，读到"状态已是处理中但 first_responded_at 是空"的中间态——SLA 结算就出错了（3.8 你会看到首次响应时间的意义）。
2. 第二条 SQL 失败，事务回滚还好；如果不小心没包事务，就永久脏数据。
3. 一条 SQL 的原子性由数据库保证，最省心。

**REPLY 的 if 条件为什么是 `first_responded_at == null`？** 只有第一次回复才记"首次响应时间"，后续回复不改它。**首次响应时间 = SLA 结算的关键证据**（第 4 篇会用到）。

## 3.8 工单创建：状态机是怎么"入伙"的？

看一下 create() 方法的关键流程（创建工单）：

```java
@Transactional(rollbackFor = Exception.class)
public TicketDO create(TicketCreateDTO dto) {
    TicketDO ticket = new TicketDO();
    ticket.setTicketNo(ticketNoGenerator.next());   // 1. Redis 生成工单号
    ...
    ticket.setStatus(TicketStatus.PENDING_ASSIGN.getCode());  // 2. 直接置"待分派"
    ticketMapper.insert(ticket);                    // 3. 插入
    // 4. 写状态日志：NEW → PENDING_ASSIGN，事件 SUBMIT（"创建即提交"）
    writeStatusLog(ticket.getId(), TicketStatus.NEW, TicketStatus.PENDING_ASSIGN,
            TicketEvent.SUBMIT, currentUserId(), "USER", "工单创建");
    // 5. 启动 SLA 计时（第 4 篇）
    slaService.createTicketSla(ticket.getId(), ticket.getPriority());
    // 6. 事务提交后，发布"工单创建了"事件（异步分派 + AI 分类的引信）
    ...
}
```

**一个有意思的细节**：创建时没有走"NEW 状态停留一段时间再 SUBMIT"，而是**创建即提交**——直接落到待分派，但流水账里完整记录了"NEW → PENDING_ASSIGN / SUBMIT"这一步。

**面试怎么讲这个设计？** "当前实现是创建即进入待分派，NEW 状态和 SUBMIT 事件在枚举和矩阵里都保留着——未来要支持草稿功能（先存着不提交），不需要改状态机任何代码，只要改 create 的插入状态并在详情页加一个提交按钮。**状态机为业务演进预留了空间**。"

## 3.9 常见疑问速答

**Q：为什么"已解决"后还要"关闭"两步？**
A：解决 = 客服说"搞定了"；关闭 = 这事正式翻篇。中间留一个窗口期：客户可能回来确认/补充（REOPEN），客服也能再检查一遍。如果解决即关闭，客户回来就得从 CLOSED 重开（权限要求更高），体验差、链路绕。

**Q：CANCELLED 为什么是死状态？**
A：取消 = 这张单作废了。如果允许复活，就会出现"作废的单被翻出来重新处理"的混乱，也会破坏审计的严肃性。客户要重新求助，请创建新工单。

**Q：非法流转会怎样？**
A：抛业务异常 ILLEGAL_TRANSITION（HTTP 409），消息里带"当前状态和事件"（如"当前状态[已关闭]不允许事件[REPLY]"），前端弹提示。测试里对 10+ 条非法组合有断言——规则不是嘴上说说，是被测试锁定的。

**Q：allowedEvents 是什么？有什么用？**
A：状态机还能告诉你"当前状态能做什么"——工单详情接口把它返回给前端，前端据此禁用/启用按钮。状态机是唯一事实，前端零状态判断逻辑（前端写死状态判断表的项目，状态机一改就前后端失联）。

## 3.10 本篇小结

- 状态机 = 状态 + 事件 + 转移规则表；工单用它管规矩、留流水、控权限。
- 8 状态（一条主流程线 + 升级/取消两个分支）、12 事件、23 条合法转移、CANCELLED 终态。
- 代码 5 个类：枚举 × 2 + Transition record + 静态注册表 + 引擎门面，核心不到 50 行。
- transition() 五步：查单 → 矩阵校验 → 权限校验 → 乐观锁条件更新（含后置动作）→ 流水账。
- 设计金句：**规则用代码固化（可测可追溯），并发用条件更新兜底（CAS 原子）**。
