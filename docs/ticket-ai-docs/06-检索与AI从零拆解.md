## 6.1 先理解"检索"：MySQL 的 LIKE 为什么不行

想象你在知识库里搜"退货政策"：

- MySQL 的 `LIKE '%退货%'`：**逐行扫**，把每篇文章从头到尾找一遍"退货"两个字——几千篇还行，几十万篇就慢了；而且搜"退款流程"搜不到"退货政策"（字面不匹配）。
- 专业搜索引擎（ES）：提前把文章**拆成词条建立索引**（倒排索引），搜的时候直接查索引——**毫秒级**，还能做相关性打分。

**倒排索引一句话**：平时我们想的是"文章 → 包含哪些词"；倒排索引反过来存"词 → 出现在哪些文章"。

```
"退货" → [文章3, 文章7, 文章12]
"退款" → [文章3, 文章9]
搜"退货" → 直接取列表 [3,7,12]，不用扫全文
```

这就是 ES（Elasticsearch）的核心能力：**全文检索 = 分词 + 倒排索引 + 相关性排序**。

## 6.2 再理解"向量检索"：把文字变成坐标

全文检索匹配"字面"，但有局限：客户说"手机屏幕碎了"，知识库里写的是"液晶面板破损"——字面完全不同，**意思一样**。全文检索找不到。

**向量检索的思路**：把一段文字变成**一串数字（向量）**——一个 1536 维的"坐标点"（由 embedding 模型转换）。意思相近的文字，坐标点也挨得近：

```
"手机屏幕碎了"      → [0.12, -0.34, 0.87, ...]  (1536个数字)
"液晶面板破损"      → [0.11, -0.33, 0.88, ...]  (离上面很近)
"今天天气不错"      → [-0.72, 0.51, 0.03, ...]  (离上面很远)
```

检索时：把客户问题也转成坐标 → **找"最近的几个邻居"（knn，k-nearest neighbors）**——语义相似的文档就出来了。

**两个检索的定位**：
- 全文检索（match）：**精确字面**，搜"退货"就是字面上的退货。
- 向量检索（knn）：**语义相近**，说"屏幕碎了"能找到"面板破损"。
- **两者互补，项目里一起用**：关键词 match 打底，向量 knn 补充语义，ES 自动合并分数排序。

**embedding 是什么**：文字 → 向量的转换过程。调用 embedding 模型的接口（如 text-embedding-3-small，输出 1536 维），一行文字换 1536 个数字。

## 6.3 项目怎么用 ES：两个索引 + 三级一致性

### 6.3.1 两个索引

```
kb_segment_index（知识库分段索引）
  id（=分段id）、kb_id、title、category、content（正文，text 可全文检索）
  content_vector（1536 维向量，cosine 相似度）

ticket_index（已解决工单索引）
  id（=工单id）、ticket_no、title、description、category
  content_vector
```

**为什么知识库要"分段"再进索引？** 一篇文章几千字，整体检索有两个问题：① token 成本（后面 RAG 要花钱喂给 LLM）；② 相关度稀释（文章 3000 字只有一段讲退货，整篇匹配分不高）。切段后每段 500 字左右，检索到哪段就取哪段——**精确命中、成本可控**。

切段规则（KnowledgeSegmenter）：按 Markdown 标题层级切（语义天然完整）；无标题的按 **500 字定长滑动窗口，重叠 50 字**——重叠防止"一句话恰好被切成两半，两边都语义残缺"。

### 6.3.2 写入链路：MySQL 是事实源，ES 可重建

```
知识库文章上架：
  文章 → 切段 → 写 MySQL kb_segment（事实落库）
       → 每段调 embedding 转向量 → upsert 写 ES（按 id 覆盖写，天然幂等）
       → ES 写失败？→ 发消息进重试队列（es-sync-retry）重试 3 次
       → 还失败？→ EsSyncCompensationTask 每 10 分钟对比 MySQL 和 ES 的 id 差集补写

工单解决（RESOLVED）：
  异步监听事件 → 写 ticket_index（标题+描述+向量）
```

**为什么是"MySQL → ES"单向？** MySQL 有事务、有约束，是数据的"事实源"；ES 只是"查询索引"，它的全部数据都能从 MySQL 重建。ES 集群炸了？删索引重建，业务数据零损失。**先写事实源，再同步索引；索引可重建，事实不能丢。**（第 1 篇那句话的又一次应用。）

### 6.3.3 查询：两种模式

```java
// 知识库检索：bool match（全文）+ 可选 knn（向量）
SearchRequest.Builder builder = new SearchRequest.Builder()
        .query(q -> q.bool(b -> {
            b.should(s -> s.match(m -> m.field("content").query(keyword)));
            b.should(s -> s.match(m -> m.field("title").query(keyword)));
            return b;
        }));
if (queryVector != null) {
    builder.knn(k -> k.field("content_vector").queryVector(向量).k(5));  // 最近的5个
}
// ES 自动合并 match 和 knn 的分数排序
```

**一个实现细节**：knn 是 SearchRequest 的**顶层参数**（builder.knn(...)），不是 bool query 里的子查询——elasticsearch-java 的 API 设计如此，写错过的人不少。

**降级**：没有向量（embedding 挂了）→ 纯全文检索；ES 挂了 → 检索接口返回空，AI 建议链路里"参考为空"，LLM 基于常识回复——**增强层故障不影响主流程**（和第 4 篇的哲学一致）。

## 6.4 AI 部分：先搞懂三个概念

### 6.4.1 LLM 怎么"调用"？

LLM（大语言模型）是一个**远程服务**：你把一段文字（prompt）通过 HTTP 发过去，它把生成的文字返回给你。OpenAI 兼容协议长这样：

```json
POST /v1/chat/completions
{
  "model": "gpt-4o-mini",
  "messages": [
    {"role": "system", "content": "你是客服工单分类器……"},
    {"role": "user", "content": "标题：手机碎了 描述：……"}
  ],
  "response_format": {"type": "json_object"},   // 要求返回 JSON
  "temperature": 0.3                             // 控制随机性
}
```

**调用 LLM 的本质就是发一个 HTTP 请求**——不是什么魔法。所以用 Java 自带的 HttpClient 就能调，不需要任何框架。

### 6.4.2 为什么要"强制 JSON 输出"？

项目里 LLM 的结果要解析成对象（分类结果、回复草稿）。如果不强制 JSON，模型可能回一段散文，解析就崩。三个手段叠加：
1. 协议层：`response_format={"type":"json_object"}`（服务端约束）。
2. 提示词层：明确写出"输出 JSON：{"category": "...", "priority": 1|2|3|4}"（给格式范例）。
3. 代码层：返回后 `objectMapper.readTree()` 校验是不是合法 JSON——**不是合法 JSON 就当调用失败，走降级**。

**提示词约束是"软约束"，代码校验是"硬约束"——永远要有代码兜底。**

### 6.4.3 为什么自己写客户端，不用 Spring AI 框架？

这是面试大概率会问到的选型问题，**答案必须是技术决策，不是"别人不让我用"**。组织好这套说法：

> "我评估过 Spring AI，最终选择自己用 JDK HttpClient 封装，基于三点考虑：
> 第一，**能力需求很窄**——我只需要 chat（对话生成）和 embeddings（向量化）两个能力，一个 HTTP 封装 170 行就能覆盖，引入框架是为了 10% 的需求付出 100% 的学习和依赖成本；
> 第二，**错误分类和降级要完全自控**——我需要把失败精确分类成『没配密钥 / 超时 / 限流 / 服务端错误 / 返回格式非法』，每种走不同的降级路径（有的静默、有的报 503、有的返回 null 交给别的策略），框架的异常体系没有这个粒度，自己封装可以完全掌控；
> 第三，**协议透明、可替换**——我直接对接 OpenAI 兼容协议，base-url 是配置项，以后换厂商（比如换成国产模型）只改配置不改代码。
> 另外我封装时把『每次调用写 ai_usage_log』做进了客户端内部，保证成本可观测——这是项目级要求，用框架反而要额外处理。"

**这个回答的要点：每个"不用框架"的理由背后都有一个具体的项目诉求**（降级矩阵、成本观测、可替换），不是为炫技而不用。

## 6.5 代码走读：LlmClient（自研客户端）

```java
@Component
public class LlmClient {
    // JDK 自带 HTTP 客户端
    private final HttpClient httpClient = HttpClient.newBuilder()
            .connectTimeout(Duration.ofSeconds(5)).build();

    /** 文本 → 向量（给 ES 检索用） */
    public float[] embed(String text) {
        if (apiKey 为空) { 记日志; throw new LlmException("LLM_API_KEY 未配置", NO_KEY); }
        // POST {base-url}/embeddings {model, input: [text]}
        // 解析返回的 data[0].embedding → float[]
        // 成功/失败都写 ai_usage_log
    }

    /** 对话并强制 JSON（给分类/建议/分派用） */
    public String chatJson(Long ticketId, String scene, List<Message> messages) {
        if (apiKey 为空) { ... throw NO_KEY; }
        // POST {base-url}/chat/completions
        //   response_format=json_object, temperature=0.3
        // 解析 choices[0].message.content
        // 校验 JSON 合法性（非法 → PARSE_ERROR）
        // 成功/失败都写 ai_usage_log（tokens、耗时、成败、错误）
    }
}
```

**错误分类**（LlmException 的 reason）：NO_KEY（没配密钥）/ TIMEOUT（15 秒超时）/ RATE_LIMIT（限流）/ SERVER_ERROR（HTTP 非 200）/ PARSE_ERROR（返回不是合法 JSON）。调用方看分类决定怎么降级。

**配置从哪来**：`app.llm.base-url / api-key / chat-model / embed-model / timeout-ms`——环境变量注入（.env 文件，不提交 git）。没配密钥时**第一行就快速失败**（NO_KEY），而不是等 15 秒超时。

## 6.6 场景一：自动分类 + 优先级建议

**目标**：工单建好后，AI 自动建议"这是什么类别、多紧急"，方便分派和统计。

**流程**：

```
工单创建（事务提交后）→ 发布事件 → 异步监听：
  1. SETNX ai:classify:{工单Id}（Redis：不存在才写入，TTL 600秒）
     → 写不进去 = 之前执行过 = 跳过！（防重复调 LLM）
  2. chatJson(CLASSIFY)：
     system: 你是客服工单分类器，输出 JSON：
             {"category": "售后|售前|投诉|咨询|其他", "priority": 1|2|3|4, "confidence": 0.0-1.0}
     user:   标题 + 描述
  3. 解析结果 → 写回 ticket 表的 ai_category / ai_priority / ai_score（建议字段！）
  4. finally：删除 SETNX key（下次还能再分类）
```

**为什么 SETNX 防重？** LLM 调用是花钱的（按 token 计费）。如果事件重复投递（MQ 重试、应用重启），同一个工单被调两次 LLM = 白花两份钱。SETNX 是"闸门"：谁先写入谁执行，后到的直接跳过。**异步任务必须自己保证幂等**——和 SLA 消息消费是同一个思想。

**为什么不直接写 category 字段？** AI 的结论是"建议"，可能错。写进 ai_* 建议字段，坐席在界面上看到建议，点"采纳"（accept-category 接口）才同步到正式字段。**AI 永远不做最终决定**——这是贯穿全项目的边界。

**降级**：LLM 挂了 → 静默（ai_category 保持空），坐席手工分类——流程零影响。

## 6.7 场景二：RAG 回复建议（项目最亮眼的功能）

### 6.7.1 什么是 RAG？

RAG（Retrieval-Augmented Generation，检索增强生成）= **给 LLM 开卷考试**。

- 不开卷（裸问）："客户问手机碎了怎么办"——LLM 只能凭训练记忆答，可能过时、可能编造公司政策。
- 开卷（RAG）：**先检索**（从历史工单和知识库里找相关资料）→ **再回答**（把资料和问题一起给 LLM，让它基于资料作答）。

**RAG 的价值**：答案有依据、能溯源（客服能点开引用核实）、不依赖 LLM 记忆公司内部信息。

### 6.7.2 完整流程

```
坐席在工单详情页点"生成建议"：
  1. 把工单（标题+描述）embed → 得到查询向量
  2. 召回（两个方向各 3 条）：
     · ES ticket_index knn：历史上"意思最像"的已解决工单 top3
     · ES kb_segment_index：知识库里相关段落 top3（match + knn）
  3. 组装 prompt（参考资料 + 问题）：
     system: 你是资深客服。参考给出的历史工单和知识库内容写回复草稿。
             输出 JSON：{"reply": "回复内容", "kbRefs": [引用标题...]}
             不超过 500 字，语气专业礼貌，不得编造不存在的政策。
     user:   客户问题: ... + 参考资料: [历史工单]... [知识库]...
  4. chatJson → 解析 → reply 超 500 字截断兜底 → 返回 {reply, kbRefs}
  5. 前端抽屉展示：草稿可编辑 + 引用条目可展开核实
  6. 坐席编辑后点"发送" → 走正常回复接口
```

### 6.7.3 三个工程细节（面试亮点）

**细节 1：引用是"召回时真实收集"的，不是 LLM 编的。** 很多 RAG 让 LLM 自己生成引用列表——模型会幻觉出不存在的文档。本项目引用列表在召回阶段就收集好（"相似工单 T2026..."、"知识库: 文章标题"），LLM 的 kbRefs 只是参考，最终以真实召回的为准。

**细节 2：500 字限制是"提示词约束 + 代码截断"双保险。** 提示词说"不超过 500 字"是软约束，模型可能不听；代码 `reply.length() > 500` 截断是硬兜底。

**细节 3："不得编造不存在的政策"不是口号。** 客服回复若编造退换货政策，公司要担法律风险。提示词明确禁止 + 人工编辑后才发送 + 引用可溯源——**三道闸**。

### 6.7.4 降级

| 故障 | 表现 |
|---|---|
| LLM 不可用 | 接口返回 503（AI_UNAVAILABLE），前端明确提示——**这个场景必须报错**，因为坐席在等结果 |
| ES 没召回 | prompt 无参考资料，LLM 基于常识回复并建议人工跟进 |
| 解析失败 | 同上，503 |

**为什么分类失败要静默、回复建议失败要报 503？** 触发方式不同：分类是后台自动任务，失败了没人等它，静默降级即可；回复建议是坐席**主动点击**等结果的操作，必须明确反馈"AI 暂不可用"，否则坐席以为在生成、白等。**降级策略跟随用户预期。**

## 6.8 场景三：AI 分派建议

```
（仅当 AI_RECOMMEND 策略启用时被工厂调用，见第 5 篇）
  1. chatJson(DISPATCH)：
     system: 你是客服排班助手，根据工单信息推荐合适的坐席。
             输出 JSON：{"agentId": 数字或null, "reason": "简短理由"}
     user: 工单标题/描述/分类
  2. agentId 为 null → 返回 null（工厂继续尝试下一个策略）
  3. LLM 异常 → 返回 null（同样交给下一个策略）
```

**降级链**：AI 挂了 → 返回 null → 工厂尝试负载/轮询 → 全失败 → 保持待分派等人工。**AI 是分派链条的锦上添花，不是必经之路。**

## 6.9 ai_usage_log：AI 成本和质量"看得见"

每次 LLM 调用（成功或失败）都写一行：场景、模型、输入/输出/总 token、耗时、成败、错误信息。

**能回答什么问题？**
- 这个月 AI 花了多少钱？（token 就是钱，sum total_tokens × 单价）
- 哪个场景调用最多？（GROUP BY scene）
- AI 最近是不是变慢了？（AVG latency_ms 趋势）
- 昨天那次分类失败是什么原因？（error_msg 留痕）

**记录失败也不能影响主流程**：recordUsage 内部 catch 一切异常只记日志——**可观测性设施永远不能成为业务的故障点**。

## 6.10 本篇小结

- 全文检索 = 分词 + 倒排索引（字面匹配）；向量检索 = embedding + knn（语义匹配）；两者互补。
- MySQL 是事实源，ES 是可重建索引；写入三级保障：同步 → MQ 重试 → 定时对账。
- LLM 调用 = 一个 HTTP 请求；JSON 输出三层保障（协议 + 提示词 + 代码校验）。
- 自研客户端的技术决策：需求窄、降级粒度要自控、协议可替换、成本观测内建。
- 三个 AI 场景全部是"建议"：分类写建议字段等采纳、回复草稿人工编辑后发送、分派推荐可被其他策略替代。
- 降级矩阵：静默 vs 503 的区别 = 后台任务 vs 主动操作。
- RAG 三件套：**检索真实引用 + 人审后发送 + 禁止编造**。
- 面试金句："**AI 是外挂不是本体：核心链路确定性代码，AI 只提建议；LLM 挂了，系统慢一点笨一点，但照常转。**"
