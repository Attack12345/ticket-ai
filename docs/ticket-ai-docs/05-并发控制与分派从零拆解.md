## 5.1 先用抢红包理解"并发问题"

假设群里发了一个红包，100 人同时抢，红包只有 1 个。

程序怎么判断"谁抢到了"？朴素写法：

```java
if (红包余额 > 0) {          // 第 1 步：读
    你抢到了！余额 = 0;       // 第 2 步：写
}
```

问题来了：100 个请求**同时**执行到第 1 步，都读到"余额 > 0"——**100 个人全抢到了**。这就是并发问题：**读和写之间有空隙，多个请求都挤进了这个空隙**。

工单系统的抢单一模一样：

```java
if (工单状态 == 待分派) {     // 读
    把工单分给我; 状态 = 处理中;  // 写
}
```

两个客服同时读"待分派"，都认为能抢，都去写——**一张单被两个人领了**。

解决方案两大类，项目里**都用上了**，下面逐个讲。

## 5.2 方案一：乐观锁（版本号）

### 5.2.1 原理

给数据加一个"版本号"字段（ticket.version）。每次更新必须带"我读到的版本号"：

```
客服A 读到：version=5
客服B 读到：version=5

客服A 更新：UPDATE ticket SET status='处理中', version=6
           WHERE id=1 AND version=5    → 成功（1 行被改）

客服B 更新：UPDATE ticket SET status='处理中', version=6
           WHERE id=1 AND version=5    → 失败（0 行！version 已经是 6 了）
```

**数据库保证：WHERE 条件匹配几行就更新几行，这是原子操作**。A 先到，version 变 6；B 的 WHERE version=5 匹配不到任何行，更新 0 行——B 就知道"我输了"。

**为什么叫"乐观"**？因为假设冲突很少发生（乐观），只在更新那一刻做校验；如果冲突频繁（悲观场景），就用另一招——锁（5.3）。

### 5.2.2 项目里的写法（关键！）

```java
UpdateWrapper<TicketDO> update = new UpdateWrapper<TicketDO>()
        .eq("id", ticketId)
        .eq("status", TicketStatus.PENDING_ASSIGN.getCode())  // 业务条件
        .eq("version", ticket.getVersion())                   // 版本条件
        .isNull("agent_id")                                   // 无主条件
        .set("status", TicketStatus.PROCESSING.getCode())
        .set("agent_id", user.getAgentId())
        .set("version", ticket.getVersion() + 1);
int rows = ticketMapper.update(null, update);
if (rows == 0) {
    throw new BusinessException(ErrorCode.CONCURRENT_MODIFY, "工单已被其他坐席领取");
}
```

**三个条件各管一件事**：
- `version = 旧版本`：防"基于过期数据的更新"（经典乐观锁）。
- `status = 待分派`：业务前置条件——管理员刚手动分派了？状态已经不是待分派，抢不了。
- `agent_id IS NULL`：语义兜底——已经有人领了，再领就是抢别人的单。

**为什么用 UpdateWrapper 手写而不是框架的 @Version 注解？** 这是项目实测踩过的坑：MyBatis-Plus 的 @Version 拦截器在某种版本组合下更新路径有缺陷（报 MP_OPTLOCK_VERSION_ORIGINAL not found），而且注解方案对"一条 SQL 里同时改状态+version+时间戳+归属"这种复杂更新不直观。**核心一致性代码手写显式 SQL，不依赖框架魔法**——这是吃过亏后的自觉。

## 5.3 方案二：分布式锁（Redisson）

### 5.3.1 乐观锁够了吗？为什么还要锁？

乐观锁的缺点是：**失败的请求也真的去执行了一次 UPDATE（虽然影响 0 行）**。10 个人同时抢，数据库要扛 10 次 UPDATE；1000 个人抢，就是 1000 次——**在高并发热点下，数据库成了瓶颈**。

锁的思路相反：**抢之前先排队，保证同一时刻只有一个人"真正干活"**——其他人在门口等着，连数据库都不用碰。

### 5.3.2 为什么叫"分布式"锁？

单机时代用 `synchronized`（Java 关键字）就行——它锁的是**当前进程内**的代码。但系统要支持多台服务器部署（横向扩展），A 服务器的 synchronized 管不了 B 服务器——**锁必须是所有服务器共享的**。共享在哪里？大家都能访问的地方：Redis。

**Redisson 是什么**：Java 的 Redis 客户端库，提供"基于 Redis 的分布式锁"开箱即用的 API。它的锁原理（简化版）：往 Redis 写一个 key，写成功 = 拿到锁；别人写同样 key 失败 = 没拿到；用完删 key = 释放锁。

### 5.3.3 抢单代码：双保险合体

```java
// 第 1 层：分布式锁（排队）
RLock lock = redissonClient.getLock("ticket:claim:" + ticketId);
boolean locked = lock.tryLock(3, 10, TimeUnit.SECONDS);  // 等待3秒拿锁，锁10秒自动释放
if (!locked) {
    throw new BusinessException(ErrorCode.CONCURRENT_MODIFY, "工单正在被其他坐席处理");
}
try {
    // 第 2 层：锁内做乐观锁更新（上一节那三条 WHERE）
    // 影响 0 行 → 抛 CONCURRENT_MODIFY
    ...
} finally {
    lock.unlock();   // 用完必须释放（finally 保证异常也释放）
}
```

参数解释：
- `tryLock(3, 10, 秒)`：最多等 3 秒拿锁（拿不到直接失败，不无限等）；拿到后锁 10 秒自动过期（防止"拿到锁的人挂了，锁永远不释放"）。
- key 设计：`ticket:claim:{工单Id}`——**锁的粒度是"一张工单"**。不同工单的抢单互不阻塞；如果锁 key 写成全局一个，所有工单的抢单都串行，性能就毁了。

**为什么锁内还要乐观锁？** 锁是"大概率有效的排队机制"，但有两类漏洞：
1. **锁过期**：业务执行超过 10 秒（极端慢），锁自动没了——第二个客服拿到锁进来抢同一张单。
2. **Redis 故障**：锁服务不可靠。

乐观锁是最后一道 CAS 防线——**无论前面发生了什么，数据库的条件更新保证最多一个人成功**。所以：**锁挡流量（把 1000 次 UPDATE 变成 1 次），乐观锁保正确（最终只能成功 1 个）**。

### 5.3.4 抢单成功后还要做什么

```java
// 1. 写状态流水账：PENDING_ASSIGN → PROCESSING，事件 CLAIM
// 2. 坐席负载 +1（SQL 原子自增，不是"读-加-写"）：
agentMapper.update(null, new UpdateWrapper<AgentDO>()
        .eq("id", user.getAgentId())
        .setSql("current_load = current_load + 1"));
```

**setSql("current_load = current_load + 1") 为什么安全？** 数据库层面原子自增——如果代码写成"先 SELECT current_load，Java 里 +1，再 UPDATE"，两个请求同时读到 3，都写 4（真实应该是 5）——这就是经典的"读-改-写"竞态。**能在 SQL 里原子完成的操作，不要在代码里拆开做**。

### 5.3.5 并发测试：10 线程抢一张单

M4 里程碑的验收测试：10 个线程同时抢同一张 PENDING_ASSIGN 工单——断言**恰好 1 个成功、9 个抛 CONCURRENT_MODIFY**，且最终 agent_id 正确、状态日志只有一条 CLAIM。**这种测试是"并发正确性"的证据，不是嘴上说说的双保险。**

## 5.4 分派：工单怎么到人手里

### 5.4.1 问题

每天几百张新工单，谁来处理？四种思路：轮流来（轮询）、谁闲给谁（负载）、谁擅长给谁（技能）、让 AI 推荐（智能）。**每一种都写成一个"策略"类，按配置的优先级顺序尝试**——这就是设计模式里的"策略模式"。

### 5.4.2 策略接口

```java
public interface DispatchStrategy {
    String type();                    // 策略编码（和数据库表 dispatch_strategy 的编码对应）
    Long dispatch(TicketDO ticket);   // 执行：返回坐席 ID，找不到返回 null
}
```

四个实现类：

**① 轮询 RoundRobinStrategy（编码 ROUND_ROBIN）**
```java
// 轮流：Redis 计数器自增，对"在线坐席数"取模
Long counter = redis.opsForValue().increment("dispatch:rr");
return online.get((int)(counter % online.size()));   // 0,1,2,0,1,2... 轮流
```
为什么用 Redis 计数？`INCR` 是原子操作，多线程下不会重号；而且计数跨实例共享（如果是每个 JVM 自己的变量，两台服务器就各轮各的）。

**② 负载最低 LeastLoadedStrategy（编码 LEAST_LOADED）**
```java
// 在线坐席按 current_load 升序排，取第一个（负载相同取 id 最小）
// 谁手上的活最少，谁接新单
```

**③ 技能匹配 SkillMatchStrategy（编码 SKILL_MATCH）**
```java
// 工单的 category（如"投诉"）在坐席的 skill_tags（["投诉","售后"]）里 → 命中
// 工单还没分类 / 没人匹配 → 返回 null（交给下一个策略）
```
注意：技能标签是 JSON 数组字符串，代码里解析失败要容错（log.warn 返回空列表，不能让一条脏数据炸掉整个分派）。

**④ AI 推荐 AiRecommendStrategy（编码 AI_RECOMMEND）**
```java
// 调 LLM：把工单信息发给模型，模型返回 {"agentId": 123 或 null, "reason": "..."}
// LLM 挂了 / 超时 / 返回 null → 返回 null（交给下一个策略）
// 这个策略默认是关闭的（enabled=0），接 LLM 后才启用
```

### 5.4.3 工厂：按配置顺序尝试

```java
public DispatchResult dispatch(TicketDO ticket) {
    // 1. 查配置表：enabled=1 的策略，按 weight 降序排
    List<DispatchStrategyDO> configs = selectEnabled().sorted(按权重降序);
    // 2. 逐个尝试，第一个返回非 null 的生效
    for (config : configs) {
        Long agentId = strategyMap.get(config.getStrategyType()).dispatch(ticket);
        if (agentId != null) {
            return new DispatchResult(agentId, strategy.type());  // 记下谁生效的
        }
    }
    return null;  // 全部失败：工单保持"待分派"，等人工
}
```

默认配置（数据库里 4 行）：轮询 100 分 > 技能 90 > 负载 80 > AI 60（关闭）。

**一个实现细节（踩过的坑）**：策略 Map 不能靠 Spring 按 bean 名自动注入——Spring 按 bean 名注入的 key 是类名小驼峰（roundRobinStrategy），和策略编码（ROUND_ROBIN）对不上。所以代码里手动注入 `List<DispatchStrategy>` 后按 `type()` 建 Map：

```java
this.strategyMap = strategies.stream()
        .collect(Collectors.toMap(DispatchStrategy::type, Function.identity()));
```

**全部失败会怎样？** 工单保持"待分派"——这不是故障，是设计内的兜底路径：坐席可以在列表里看到它并**抢单**，管理员也能**手动分派**。**自动分派是尽力而为的优化，人工兜底永远存在。**

### 5.4.4 分派成功后（衔接状态机）

```java
// 自动分派命中 → 走状态机：SYSTEM 事件 AUTO_ASSIGN
ticketService.transition(ticket.getId(), TicketEvent.AUTO_ASSIGN, null, "SYSTEM",
        agentId, groupId, strategy);
// 同一条 UPDATE 里：状态 → 处理中、写上 agent_id/group_id、记下 assign_strategy
```

`assign_strategy` 字段就是"这次分派是哪个策略成功的"——运营能统计各策略命中率，出问题能追责。**可观测性字段，成本一行，价值长期。**

### 5.4.5 异步分派：为什么不在创建工单时同步分派？

```java
@EventListener                       // 监听"工单创建了"事件
@Async("dispatchExecutor")           // 异步线程池执行
public void onTicketCreated(TicketCreatedEvent event) {
    dispatchAsync(event.ticket());
}
```

原因：创建接口要快速响应客户（"您的工单号是 XXX"）；分派要查配置、查坐席、可能调 AI（最慢 15 秒超时）——同步做，客户提交表单要等半天。**异步化：客户先拿到工单号，分派在后台悄悄完成**；分派失败也不影响创建成功（保持待分派 + 抢单兜底）。

**事件在"事务提交后"才发布**（afterCommit 钩子）——保证异步任务读到的数据是已提交的，不会读到半成品。

## 5.5 面试追问的四个"如果"

**Q1：锁 10 秒过期了怎么办？**
乐观锁兜底：锁内 UPDATE 的 WHERE version 条件保证即使第二个客服拿到了过期后的锁，也抢不过"已经更新过 version 的"第一个人。最坏结果：多打了一次数据库，业务不出错。

**Q2：Redis 整个挂了，抢单还能用吗？**
tryLock 会失败/抛异常 → 抢单接口暂时不可用（提示稍后重试）——**但没有脏数据**，因为即使有人绕过锁直接执行，乐观锁依然保证一致性。正确性靠数据库，Redis 只是性能优化。另外管理员手动分派不受影响（不需要锁）。

**Q3：current_load 会不会不准？**
当前实现维护点只有两处（抢单 +1、关闭 -1）；工单被"重派"等边缘场景没有做 -1——这是已知的简化，严谨做法是重派时给旧坐席 -1，或者干脆不冗余、实时 COUNT。**面试主动说"我清楚这里的边界"比被问住好一百倍。**

**Q4：为什么不用数据库的行锁（SELECT ... FOR UPDATE）？**
悲观锁也可以（SELECT 时锁行，别人等），但：① 要开事务并持锁到事务结束，锁的时间长；② 热点行竞争下所有请求都在数据库排队等待，数据库连接被占满的风险更高；③ 分布式场景下锁由数据库承担，扩展性差。**抢单这种"竞争激烈但单次操作极快"的场景，Redis 锁 + 乐观锁是更优组合。**

## 5.6 本篇小结

- 并发问题 = 读和写之间有空隙，多人挤进去。解法：条件更新（乐观锁）或互斥（锁）。
- 乐观锁：WHERE version=旧值，影响 0 行 = 输。项目用 UpdateWrapper 手写，不靠框架注解。
- 分布式锁：Redis 共享互斥，锁粒度一张工单；tryLock(等待3s, 租约10s)。
- 双保险：**锁挡流量，乐观锁保正确**——1000 次尝试只有 1 次真 UPDATE，且最多 1 人成功。
- 原子操作在 SQL 里做（current_load 自增），不在代码里"读-改-写"。
- 分派：策略模式四实现 + 表驱动权重 + 工厂顺序尝试 + 全失败人工兜底 + 异步执行。
- 面试金句："**能排队就不打架，能原子就不拆开，兜底永远存在。**"
