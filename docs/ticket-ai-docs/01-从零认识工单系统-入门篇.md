# TicketAI 学习手册 · 第 1 篇：从零认识工单系统（入门篇）

> 本系列共 7 篇，写给"完全不了解这个项目"的你，假设你只知道 Java 基础语法，没接触过 Redis、MQ、ES、JWT 这些中间件。每篇从生活类比开始，把概念讲透再进入项目代码。
>
> **本篇目标**：看完后你能用大白话讲清楚"这是一个什么系统、为什么需要它、每个技术组件是干什么的、一次请求是怎么走完全程的"。

## 1.1 先回答一个最基础的问题：什么是"工单"？

想象你是一个电商公司的客服。

客户打电话来："我昨天买的手机收到是碎的！"

你要怎么处理这件事？如果只是在电话里说"好的我们处理"，然后挂断——大概率这事就石沉大海了，客户三天后再打来发现没人跟进，暴怒投诉。

正确做法是**把这件事记下来，变成一条有编号、有状态、有人负责、有处理记录的任务**，比如：

```
工单 #T202608180001
标题：客户反映手机碎裂
状态：待处理
负责客服：张三
处理过程：已联系客户补发新机 → 客户确认收到 → 关闭
```

这张"记录 + 跟踪"的卡片，就是工单（Ticket）。**工单系统就是把"客服接待"这件事从"电话里聊两句"变成"有据可查、有始有终的流程"**。

我们这个项目做的，就是这样一个企业级工单系统，只不过它不只有"记录"这一个功能，还做了四件更高级的事（下面 1.2 讲）。

---

## 1.2 这个系统解决了哪四个问题？

**问题一：工单的"一生"需要被严格管理**

一张工单从客户进线到关闭，会经历很多阶段：

```
客户提问题 → 等人处理 → 客服处理中 → 等客户回复 → 已解决 → 已关闭
```

问题来了：每个阶段**能做什么、不能做什么**必须有规矩。比如"已关闭"的工单不能再被随意改成"处理中"（除非客户又回来追问，那叫"重开"）。如果谁都能随便改状态，工单记录就乱了，出了纠纷谁也说不清。

系统的方案是**状态机**——一张"哪些状态允许变成哪些状态"的规则表，所有状态变化必须照表执行。（第 3 篇专门拆解）

**问题二：服务质量必须被"承诺"和"监督"**

客服行业有句老话：客户可以接受问题没解决，但不能接受没人理。

所以企业会给客服定承诺："客户发来的问题，**2 小时内必须有人首次响应**，24 小时内必须解决"。超时了怎么办？系统要自动发现、自动升级（比如上报组长），不能靠人肉盯。

系统的方案是 **SLA 引擎**——到点自动检查、超时自动升级、消息丢了还有兜底扫描。（第 4 篇专门拆解）

**问题三：工单要分给"最合适的人"**

每天几百张工单，谁来处理？手动分配太累，乱枪打鸟效率低——投诉单应该给擅长处理投诉的客服，新客户咨询应该给空闲的人。

系统的方案是**分派策略**：轮询（轮流）、按负载（谁闲给谁）、按技能（谁擅长给谁）、甚至 AI 推荐，按配置的优先级自动尝试。（第 5 篇专门拆解）

**问题四：客服回复质量可以"开外挂"**

客服打字慢、记不住公司政策、同类问题每天回答一百遍。能不能让 AI 帮忙？

系统的方案是**三个 AI 增强场景**：自动给工单分类（方便分派和统计）、根据历史相似工单和知识库生成回复草稿（客服改改就能发）、推荐处理人。注意是"增强"——**AI 挂了系统照常运转，它只是建议，人做最终决定**。（第 6 篇专门拆解）

## 1.3 技术栈扫盲：每个组件是干什么的？（重点）

这是面试官第一个会问的：**"你项目里用了 MySQL、Redis、RocketMQ、Elasticsearch，它们各自是干什么的？"**

如果你现在只答得出来"MySQL 是数据库"，那你已经输了。我们用生活类比把每个都讲透。

### 1.3.1 MySQL —— 系统的"总账本"

**干什么**：存所有业务数据的最终记录——用户、工单、日志、知识库文章，全在里面。

**类比**：公司的财务总账本。任何一笔业务（创建工单、回复、改状态）都要在账本上留下记录，账本丢了公司就完了。

**特点**：
- 支持事务（ACID）：一个操作要么全成功要么全失败。比如"改工单状态 + 写一条状态日志"必须一起成功，不能状态改了日志没写上。
- 支持约束：比如"工单编号不能重复"这种规则，数据库层面直接卡死。
- 缺点：数据多了查询会慢，全文搜索很弱（后面看 ES 的戏份）。

### 1.3.2 Redis —— 系统的"便利贴墙"

**干什么**：内存里的键值存储（key-value），读写极快。本项目用它做四件事：
1. **计数器**：工单编号 `T+日期+000001` 的序列号，用 `INCR` 原子自增，多个人同时生成也不会撞号。
2. **分布式锁**：两张工单同时被抢时，谁先抢到（后面细讲）。
3. **防重复标记**：AI 分类任务只执行一次，用 SETNX（"不存在才写入"）做闸门。
4. **登录凭证存储**：refreshToken 存在这里，可以随时作废。

**类比**：办公室的便利贴墙。重要但不需要记进总账本的事（当前计数、临时标记、谁在登录），贴墙上，看和改都快；墙烧了，重新贴就行——**Redis 里的数据丢了不影响账本，这才是正确用法**。

**特点**：快（内存）、支持原子操作（INCR/SETNX/Lua 脚本）、数据可设过期时间（TTL）。

### 1.3.3 RocketMQ —— 系统的"快递驿站"

**干什么**：消息队列（MQ，Message Queue）。A 系统/模块把消息（比如"工单创建了"）投递给驿站，B 系统/模块从驿站取消息处理。两边**不用同时在线**，也不用互相等待。

**本项目两个用法**：
1. **异步通知**：工单创建成功后，发一条"工单创建了"的消息，后台自动分派、AI 分类模块收到消息各自开工——创建接口不用等它们干完就返回。
2. **延迟消息**（本项目精华）：说好"2 小时内首次响应"，那就发一条"2 小时后检查这张工单"的消息，**到点自动投递**，消费者收到就检查超时没有。（第 4 篇细讲）

**类比**：你在淘宝下单，商家发货后快递驿站帮你把包裹送到——你不需要知道快递员几点出发，驿站会按时间处理。延迟消息就像"预约快递"：说好下午 3 点送，驿站到点才出动。

**特点**：异步解耦（生产者和消费者互不等待）、可靠投递（消息丢了可重试）、延迟消息（到点投递）。

### 1.3.4 Elasticsearch（ES）—— 系统的"图书馆检索系统"

**干什么**：搜索引擎。数据写进 ES 后，可以按关键词搜（"所有提到'退货'的工单"），还可以按语义搜（"和这条工单内容意思差不多的历史工单"）。

**类比**：图书馆。MySQL 是仓库（书按编号放在架子上，你要找"提到退货的书"得一本本翻）；ES 是检索目录+索引卡片（把每本书的内容拆成词条建立索引，还能按"主题相近"推荐）。书本身放仓库，目录放检索台。

**本项目两个索引**：知识库文章的分段（给 AI 回复建议当参考资料）、已解决工单（找"历史上类似问题怎么解决的"）。

### 1.3.5 JWT —— 系统的"出入证"

**干什么**：登录认证。用户登录成功，服务器签发一张带签名、带有效期、带用户权限的"卡片"（一串字符串）；之后每次请求带上它，服务器验一下签名就知道"你是谁、有什么权限"，不用每次查数据库。

**类比**：公司门禁卡。卡片里写了你所在的楼层权限，门禁机器只验卡不查人。卡片会过期（30 分钟），过期了拿"续期卡"（refreshToken，7 天）换新卡。

### 1.3.6 LLM（大语言模型）—— 系统请的"外包专家顾问"

**干什么**：ChatGPT 这类模型。系统通过 HTTP 接口调用（OpenAI 兼容协议），让它做三件事：给工单分类、根据参考资料写回复草稿、推荐处理人。

**类比**：公司请的外包顾问。有疑难问题打电话问顾问（发 HTTP 请求），顾问给建议（返回 JSON），**但拍板永远是自家员工**——顾问今天联系不上（LLM 挂了），业务照常做，只是慢一点、笨一点。

**关键认知**：本项目 LLM 调用是自己用 Java 的 HttpClient 封装的（没有用 Spring AI 框架），为什么？第 6 篇详细讲这个决策。

### 1.3.7 一张表总结

| 组件 | 大白话角色 | 丢了会怎样 | 本项目存什么 |
|---|---|---|---|
| MySQL | 总账本 | 数据全完，必须备份 | 用户/工单/日志/知识库全量数据 |
| Redis | 便利贴墙 | 重贴即可，业务不损 | 计数器/锁/防重标记/登录凭证 |
| RocketMQ | 快递驿站 | 消息丢，但有扫描兜底 | SLA 延迟检查消息、异步通知 |
| Elasticsearch | 图书馆检索目录 | 重建索引即可 | 知识库分段、已解决工单（可重建） |
| JWT | 出入证 | — | 登录凭证（签名自校验） |
| LLM | 外包顾问 | 系统降级运行 | 不存数据，只输出建议 |

**看到没有？这里面有个贯穿全文的智慧：重要的东西放账本（MySQL），辅助的东西都可以丢（Redis/ES/MQ/LLM）——因为它们丢了，账本还在，系统就能恢复。** 记住这句话，后面每篇都会用到。

## 1.5 一次请求的完整旅程（故事版）

跟着一张"客户在网页上提交问题"的工单走一遍，把上面所有组件串起来：

```
第 1 步：客户在网页表单填了"手机碎了，求售后"点提交
  → 请求到达后端 /api/v1/channels/web-api/tickets（客户渠道接口）

第 2 步：后端做"幂等检查"
  → 客户提交时带了一个唯一编号 messageNo（比如浏览器生成的 UUID）
  → 查 MySQL：这个编号的工单建过吗？建过就直接返回旧工单（防止客户手抖点了两次提交）
  → 没建过 → 继续

第 3 步：创建工单（一个数据库事务里完成三件事）
  → Redis INCR 生成工单编号 T202608180001
  → MySQL 插入 ticket 记录（状态=待分派）
  → MySQL 插入一条状态日志（"创建"事件）
  → 建 SLA 计时单：按工单优先级匹配策略 → 算出"2小时内必须首次响应、24小时内解决"
  → 给 RocketMQ 投两条延迟消息："2小时后检查这张单有没有人响应"、"24小时后检查解决没有"

第 4 步：事务提交成功，返回给客户"您的工单号是 T202608180001"
  → 同时悄悄通知两个"后台模块"开工（发一条"工单创建了"的普通消息）：
     · 分派模块：查策略配置 → 轮询选出一个空闲客服 → 把工单分派给他（状态变"处理中"）
     · AI 分类模块：调 LLM → 得到"分类=售后，优先级=2"→ 存进"建议字段"

第 5 步：客服登录系统（JWT 出入证）看到新工单，点"领取"
  → Redis 分布式锁：防止两个客服同时抢这张单（只有一个能成功）
  → 乐观锁：数据库层面再防一次并发（第 5 篇细讲）
  → 工单状态变"处理中"，客服的负载数 +1

第 6 步：客服点"生成 AI 回复建议"
  → 后端把工单内容转成"坐标向量"（embedding）
  → 去 ES 搜："历史上有没有类似的已解决工单？知识库里有没有相关政策？"
  → 把搜到的资料塞进给 LLM 的提示词（开卷考试）→ LLM 生成回复草稿
  → 客服看看改改，点发送 → 回复成功，首次响应时间被记录
  → （2 小时后延迟消息到达，检查发现"已响应"→ 结算"按时"，不升级）

第 7 步：客户确认问题解决，客服点"解决"→ 再点"关闭"
  → 工单一生结束。已解决的工单会被同步进 ES，成为未来 AI 建议的参考资料

第 8 步：老板打开统计看板
  → "SLA 按时率 92%、平均首次响应 35 分钟、今天新增 128 单、处理中 45 单"
  → 数据全部来自 MySQL 的统计查询
```

这一遍走下来，你已经比 80% 的人更懂这个项目了。

## 1.7 本篇小结

- 工单 = 一条有始有终的服务任务记录；工单系统 = 管理工单一生的平台。
- 本项目四个核心能力：状态机管规矩、SLA 管承诺、分派管分配、AI 管提效。
- 六大组件角色：MySQL 总账本、Redis 便利贴墙、RocketMQ 快递驿站、ES 图书馆目录、JWT 出入证、LLM 外包顾问。
- 贯穿全项目的设计智慧：**重要的放账本，辅助的可丢失，账本在系统就能恢复**。
- 一次请求全链路：幂等检查 → 建单事务（含 SLA 计时+延迟消息）→ 异步分派+AI 分类 → 客服抢单（锁+乐观锁）→ AI 建议（ES 召回+RAG）→ 结算关闭 → 看板统计。
